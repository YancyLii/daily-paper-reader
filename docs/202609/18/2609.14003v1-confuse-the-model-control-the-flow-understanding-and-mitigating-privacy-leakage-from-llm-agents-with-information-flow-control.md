## 摘要
构建于大型语言模型（LLM）之上的个人AI智能体越来越能够访问用户的私人数据和通信，以提供个性化协助。这种访问带来了持续的隐私风险：智能体必须决定是否应将特定敏感信息披露给特定方。现有防御措施通过更强的系统提示、训练或显式同意检查程序，使智能体后端的LLM更具隐私保护性，但该方法存在结构性挑战：只要执行机制是由LLM在对手所控制的同一对话上下文中做出的判断，执行机制与攻击面就会重合。我们通过三种只需普通智能体交互、无需提示注入的新攻击展示了这一点：协作工作空间引诱将提取尝试重新包装为协作工作；语义混淆攻击通过省略而非智能体所写内容诱导披露；信道解耦攻击将提取请求与披露拆分到相互独立的信道。这三种攻击的泄露率都显著高于这些防御原本旨在抵御的攻击。基于这一观察，我们提出了FLOWSEAL：一种通过位于LLM上下文之外的工具级拦截器来强制执行机密性保护的防御方法，其基础是数据来源和带受控降密的信息流控制格。通过在三个基准、五个基于提示的基线和八种攻击（包括一个通过MCP执行实时工具调用的真实智能体）上的评估，FLOWSEAL将泄露率降低到接近零（例如，针对协作工作空间引诱从52.2%降至0.5%），同时保持任务效用，且与底层LLM后端无关。

## Abstract
Personal AI agents built on large language models (LLMs) are increasingly given access to a user's private data and communications in order to provide personalized assistance. This access creates a persistent privacy risk: the agent must decide whether a given sensitive information should be disclosed to a particular party. Existing defenses address this by making the agent's backend LLM more privacy-preserving through stronger system prompts, training, or explicit consent-checking procedures, but this approach has a structural challenge: whenever enforcement is a judgment the LLM makes over the same conversational context an adversary controls, the enforcement mechanism and the attack surface coincide. We demonstrate this against existing defenses with three new attacks that require only ordinary agent interaction and no prompt injection: Collaborative Workspace Lure reframes an extraction attempt as collaborative work; Semantic Obfuscation Attack induces disclosure through omission rather than through anything the agent writes; and Channel Decoupling Attack splits the extraction request and the disclosure across independent channels. All three achieve substantially higher leak rates than the attacks these defenses were originally designed to withstand. Guided by this observation, we present FLOWSEAL, a defense that enforces confidentiality through a tool-level interceptor outside the LLM's context, grounded in data provenance and an information-flow-control lattice with controlled declassification. Evaluated across three benchmarks, five prompt-based baselines, and eight attacks, including a real agent executing live tool calls through MCP, FLOWSEAL reduces leak rates to near zero (e.g., 52.2% to 0.5% against Collaborative Workspace Lure) while preserving task utility, regardless of the underlying LLM backend.

## 2. 论文提出的方法论

- **核心思想**：隐私的强制执行不能寄希望于 LLM 对对话上下文的判断，而应放在攻击者无法操纵或重定义的代码层。FLOWSEAL 通过**工具级拦截器（tool-level interceptor）**，在工具调用边界强制实施数据来源（data provenance）与信息流控制（IFC）策略。
- **两层架构**：
  - **协作层（cooperative layer）**：提示 + 四个隐私 API，帮助智能体发现受保护记录、请求授权、检查数据所有者、降密。该层不是安全关键，即使被欺骗，强制层仍能阻断泄露。
  - **强制层（mandatory layer）**：代码拦截器，中介每一次外部写入/分享调用，独立于 LLM 的语义判断。
- **关键组件**：
  - **私有数据存储**：敏感记录注册其所有者、类别、原始文本和授权主体集合。
  - **污点追踪器（taint tracker）**：按 IFC 策略维护会话污点，读取受保护记录后上下文被标记，派生内容继承来源标签。
  - **释放边界（release boundary）**：对每个写/分享调用，检查目的地类别（信任/不信任/未知）、污点状态，必要时调用内容检查器。
  - **内容检查器（declassification oracle）**：独立的 LLM 调用，只接收（受污染记录，拟输出），返回 SAFE 或 BLOCKED，不带解释以减少泄露面。它**不受代理主对话上下文影响**，由拦截器无条件触发。
- **安全格与形式化**：
  - 定义三级安全格 \( \mathcal{L} = \{\bot, \text{agent}, \top\} \)，其中 \( \top \) 表示数据主体的敏感记录，agent 表示智能体读取后的上下文，\( \bot \) 表示外部接收者。
  - 标签传播：读取 \( o \) 后上下文标签更新为 \( \ell(ctx) \leftarrow \ell(ctx) \sqcup \ell(o) \)；派生对象 \( o' \) 标签为所有来源的并集 \( \ell(o') = \bigsqcup_{i=1}^k \ell(o_i) \)。
  - 释放规则：写 \( c \) 到目的地 \( d \) 允许当且仅当 \( \ell(c) \sqsubseteq \ell(d) \) 或 \( \text{declassify}(c,d)=\text{SAFE} \)。
  - 定理 1 证明：在 FLOWSEAL 下，任何从 \( \top \) 标记记录派生的内容都不能写入 \( \bot \) 目的地，除非降密函数错误返回 SAFE，这提供了类似 Bell-LaPadula “不向下写”的性质。

## 6. 论文的主要结论与发现

- **现有提示级防御存在根本缺陷**：SPR-D2 等即使采用状态机，也无法抵抗不触发“信息请求”语义的新攻击。CWL、SOA、CDA 在 SPR-D2 上的条目级泄露率分别达到 52.2%、75.6%、43.8%，而 SPR 原有攻击 A2/A3 只有 1.9–3.0%。
- **FLOWSEAL 显著降低泄露**：针对 CWL，LR_I 从 SPR-D2 的 52.2% 降至 0.5%；SOA 从 75.6% 降至 2.3%；CDA 从 43.8% 降至 2.2%。在三个基准、八类攻击下，FLOWSEAL 总体条目级泄露率保持在 0–3.3%。
- **效用保持良好**：FLOWSEAL 在良性任务上效用为 72.4%，接近最优基线 SPR-D1 的 75.9%，同时泄露大幅低于 SPR-D1。
- **后端 LLM 无关**：更换智能体模型（DeepSeek-V3.2 → GPT-4.1-mini → Gemini-Flash-2.5）时，SPR-D2 泄露率保持高位（52.2/59.2/61.9），而 FLOWSEAL 保持低位（0.5/1.9/0.6）。
- **实时部署有效性**：在真实 Gmail/Notion 的 MCP 环境中，PrivacyChecker 对 SOA 的 LR_I 为 34.7%，FLOWSEAL 将其降至 0.0%。

## 7. 优点

- **结构性创新**：将隐私强制执行从模型上下文转移到工具调用边界，从根本上切断“攻击面与执行机制重合”的问题，思路清晰且有理论支撑。
- **形式化保障**：采用信息流控制格和受控降密，给出类似 Bell-LaPadula 的 no-write-down 定理证明，为安全性质提供数学基础。
- **双层设计合理**：协作层不承担安全关键责任，强制层即使模型被完全欺骗也能兜底；内容检查器与主对话上下文隔离，减少语义混淆影响。
- **实验全面**：覆盖多个基准、防御、攻击、后端模型、消融，并包含真实 MCP 部署，证据链完整。
- **实用性强**：不需要修改底层工具或服务，能作为 MCP 层适配器部署；额外成本适中；承诺开源。

## 8. 不足与局限

- **内容检查器仍有残余风险**：降密函数可能出现漏检（如语义改写、复合句中嵌入敏感值）或过度拦截（误报），且实时测试中曾出现因记录未注册导致的失败案例（ConVerse 中高血压未标记为受保护，被 SAFE 放行）。
- **威胁模型有限**：本文明确不处理提示注入攻击（PIA）、工具实现被攻破、元数据投毒、侧信道等；对 PIA 仅建议用外部过滤器，未在防御内解决。
- **实时环境验证规模小**：真实 Gmail/Notion 的 MCP 实验只覆盖 SOA 等少量场景，未在真实环境中大规模复现所有攻击和基准。
- **授权场景表现保守**：在允许授权共享的实验中，FLOWSEAL 的授权披露率（ADR）低于基线，倾向于不主动发起同意请求，可能影响合法数据共享体验。
- **成本与延迟增加**：FLOWSEAL 比无防御增加约 37% 延迟，每轮成本略高（$0.109 vs $0.092），在追求低延迟或低成本的应用中需要权衡。
- **基准适配可能引入偏差**：PrivacyLens 和 ConVerse 的种子通过合成方式转换为 SPR 格式，可能改变原始攻击语义；部分基线如 FAN-LCF 被裁剪，未必反映完整防御能力。
