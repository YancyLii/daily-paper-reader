## 摘要
大语言模型（LLMs）生成寄存器传输级（RTL）代码，其功能正确性快速提升。然而，LLM 生成代码的安全性主要针对软件进行了研究；软件中的缺陷在部署后仍可修补，而不安全的 RTL 一旦流片为硅片，就没有这种补救机会。我们构建了 SECRTL-GEN，一个以真实 SoC IP 为基础的多语言资源访问安全基准：涵盖 5 个 CWE 家族和 4 种 HDL（Verilog、SystemVerilog、VHDL 和 Python）的 392 个任务，每个任务都配有黑盒功能测试平台和安全测试平台。功能规范有意省略安全义务，这与实践中功能文档常常不包含安全义务的情况一致。对五个前沿 LLM 的实证研究显示出显著差距：在普通提示下，它们在大约 73–79% 的用例中通过功能测试，但仅在 14–35% 的用例中通过安全测试，而且功能能力更强的模型并不更安全。加入 CWE 知识可提高安全性，而无辅助的自我思考帮助较小；两种以安全为导向的提示都会降低功能通过率，表明瓶颈在于规范中缺少对安全弱点的意识，而不是模型无法编写具有防御性的 RTL。我们提出了 RTL-Obliger，一个推断这些隐式义务的神经符号框架。先由 LLM 从规范中提取功能语义图；随后，符号引擎将其与 CWE 模式本体进行匹配，以发现缓解证据缺口和信号级义务；最后，LLM 在这些义务的约束下，通过保持功能的两阶段生成方式修改 RTL。在五个模型和四种语言上，RTL-Obliger 将平均全部通过率从 49.6–51.4%（SecV/RESCUE）提高到 61.6%，安全率和功能率均高于这些安全生成基线。

## Abstract
Large Language Models (LLMs) generate register-transfer-level (RTL) code with rapidly improving functional correctness. Security of LLM-generated code, however, has been studied mainly for software, where flaws can still be patched after deployment. Insecure RTL offers no such remedy once taped out into silicon. We construct SECRTL-GEN, a multi-language resource-access security benchmark grounded in real SoC IP: 392 tasks over five CWE families and four HDLs (Verilog, SystemVerilog, VHDL, and Python), each with black-box functional and security testbenches. Functional specifications intentionally omit security obligations, matching how obligations are often kept out of functional docs in practice. An empirical study of five frontier LLMs shows a sharp gap: under vanilla prompts they pass functional tests in about 73-79% of cases but security tests in only 14-35%, and stronger functional models are not safer. Adding CWE knowledge raises security, while unaided self-thinking helps less and both security-oriented prompts cut functional pass rates, showing that the bottleneck is missing weakness awareness in the specification, not an inability to write defensive RTL. We present RTL-Obliger, a neuro-symbolic framework that infers these implicit obligations. An LLM extracts a functional-semantic graph from the specification; a symbolic engine then matches it against a CWE pattern ontology to surface mitigation-evidence gaps and signal-level obligations; the LLM finally revises RTL under those obligations in a functionality-preserving two-stage generation. Across five models and four languages, RTL-Obliger raises mean all-pass from 49.6-51.4% (SecV/RESCUE) to 61.6%, with higher security and functional rates than these secure-generation baselines.

## 1. 论文的核心问题与整体含义

- **研究背景**：大语言模型（LLM）生成 RTL 代码的功能正确性快速提升，但安全性研究主要停留在软件领域。软件漏洞可在部署后修补；而 RTL 一旦流片为硅片，安全缺陷无法在线上修复，后果不可逆。
- **核心问题**：功能规范通常只描述模块“应该做什么”，而许多安全约束（如敏感数据清除、访问控制）往往存在于单独的安全配置、威胁模型或检查清单中，作者称之为**隐式安全义务**。标准 RTL 生成基准几乎不包含安全义务内容，导致即使功能通过，硬件仍可能不安全。
- **整体含义**：需要量化“功能—安全差距”，并探索从功能规范中推断缺失安全义务的方法，从而在不破坏功能的前提下生成更安全的 RTL。

## 2. 论文提出的方法论

### 2.1 SECRTL-GEN 基准构建
- **范围**：选择 5 个 CWE 家族（CWE-226、CWE-1189、CWE-1256、CWE-1260、CWE-1262），聚焦资源访问类安全弱点。
- **来源**：从 OpenTitan、Hack@DAC 2021、CVA6/Ariane、PULP Platform 四个真实开源 SoC 项目中提取 98 个唯一设计，并扩展为 4 种 HDL（Verilog、SystemVerilog、VHDL、Python/Amaranth），共 392 个语言实例。
- **任务构成**：每个实例包含功能规范、黄金实现、功能测试平台和安全测试平台；功能规范有意省略安全义务。
- **质量保证**：黄金实现行覆盖率平均 95.84%；由 3 位工程师独立人工评审，检查规范清晰性、黄金实现正确性、测试平台安全性完整度。

### 2.2 RTL-Obliger 神经符号框架
核心思想：将隐式安全义务视为 **缓解证据缺口**——规范显示了弱点前置条件（如可重用秘密寄存器被写入），但没有显示必需缓解措施（如完成时清零）。通过匹配 CWE 模式本体，将义务推断转化为确定性信号级缺口检查。

#### 主要流程
1. **功能语义图（FSG）提取**：LLM 根据规范生成结构化图 `Gspec = (E, T, S)`，使用封闭词汇表 Σ（Kind、Lifetime、Sens、Op、Guard、Exit）标注元素、转移和控制阶段。
2. **CWE 模式本体匹配**：符号引擎将 `Gspec` 与预定义的 CWE 模式图 `Gonto` 匹配，检查结构前置条件与必需缓解证据是否存在。
3. **符号义务推断**：
   - 触发条件：所需元素/转移模式存在、上下文转移匹配、且存在未覆盖元素 `U`。
   - 匹配公式包括元素匹配、转移匹配（操作、守卫、退出阶段、目标绑定）。
   - 输出信号级义务 `o = (sc, cwe, U, text)`，其中 `U` 为未覆盖元素集合。
4. **LLM-as-Judge 过滤**：LLM 重新检查候选义务是否适用于当前规范，只能保留或拒绝，不能新造义务。
5. **两阶段生成**：首先生成功能草稿 `c0 ~ Gθ(s)`；然后在 `O′` 义务引导下局部修订 `c* ~ Gθ(c0 || O′)`，避免一次性安全提示造成的功能损失。

## 3. 实验设计

- **数据集**：SECRTL-GEN，392 个任务，5 类 CWE，4 种 HDL。
- **评测模型**：5 个前沿 LLM：GPT-5.6-Luna、Mimo-v2.5-Pro、MiniMax-M3、GLM-5.2、DeepSeek-v4-Pro，均通过官方 API 零样本调用（温度 0.6，非思考模式）。
- **提示策略**：
  - L0（普通提示）：仅给功能规范。
  - L1（自我思考）：先要求模型写安全分析，再生成 RTL。
  - L2（CWE 知识）：提供对应 CWE 条目，模型自行分析义务并生成。
- **对比方法**：
  - SecV：硬件 CWE 知识图谱探索 + 安全子图检索。
  - RESCUE：RAG 方法，检索 CWE 指南和安全代码片段。

- **评测指标**：功能通过率 F、安全通过率 S、全通过率 A（同时满足 F 和 S）；每个配置重复 5 次，报告均值±标准差。
- **仿真器**：Verilog/SystemVerilog 用 Icarus Verilog，VHDL 用 GHDL，Python 用 Amaranth 内置仿真器。

## 6. 主要结论与发现

- **功能—安全差距显著**：普通提示下，五模型功能通过率约 73–79%，但安全通过率仅 14–35%；功能能力更强的模型并不更安全。
- **CWE 知识有效**：提供 CWE 知识（L2）后，平均安全通过率从 23.3% 提升到 59.4%，说明瓶颈在于规范缺少弱点意识，而非模型无法编写防御性 RTL。
- **自我思考作用有限**：L1 提升安全至 54.2%，但仍低于 L2 的 59.4%；两种安全提示都降低功能通过率（从 76.3% 降至约 60%），全通过率被封顶在约 50%。
- **RTL-Obliger 效果显著**：平均全通过率从 SecV 的 49.6% 和 RESCUE 的 51.4% 提升到 61.6%，功能率和安全率均高于基线；所有模型中全通过率提升均具有统计显著性（p ≤ 0.0085）。
- **消融发现**：符号推理是最重要组件，移除后平均全通过率从 57.8% 降至 49.7%；LLM-as-Judge 和两阶段生成提供较小但互补的增益。
- **失败原因**：73.2% 的失败发生在义务引导生成阶段，21.2% 因符号匹配漏掉正确 CWE，过滤和 FSG 提取仅占少数，未来应重点改进生成修订和匹配召回。

## 7. 优点

- **贴近实际**：基准源自真实 SoC IP，而非合成示例，覆盖 4 种 HDL，并提供黑盒安全测试平台和人工评审。
- **神经符号结合**：符号引擎提供可审计、透明的信号级义务推断，比纯 LLM 猜测更可靠；推导过程可追溯到结构证据和 CWE 场景。
- **功能保持设计**：两阶段生成将功能草稿与安全修订分离，避免传统安全提示对功能造成较大损害。
- **评估充分**：多模型、多语言、多提示策略，包含统计检验、消融实验和错误分析，结论有实证支撑。
- **成本优势**：相比多智能体方法，RTL-Obliger 在更低 token 成本和调用次数下获得更高全通过率。
- **可复现**：提供 GitHub 开源，便于后续研究复现和扩展。

## 8. 不足与局限

- **威胁模型较窄**：仅覆盖 5 类资源访问 CWE，且限于黑盒端口可观察属性；不适用于侧信道攻击、故障注入等需要白盒或内部信号分析的弱点。
- **测试平台是近似**：黑盒安全测试平台只能作为安全义务的操作性近似，不能证明义务真正满足（这在论文中已说明）。
- **语言表现不均**：VHDL 在所有方法上的通过率明显偏低（全通过率约 28–55%），这可能限制多语言结论的普适性。
- **智能体和消融实验单次运行**：智能体对比和部分消融实验仅运行一次，结果受随机性影响，统计稳健性不足。
- **基线重实现可能偏差**：SecV 和 RESCUE 是重实现并适配，不是原始发布版本，可能无法完全反映原方法性能。
- **模型范围有限**：评估的 5 款模型均为闭源前沿模型，未涵盖开源可复现模型或微调场景；不同模型对 Judge 过滤等组件表现差异明显。
- **本体范围固定**：CWE 模式本体由人工依据 MITRE 定义构建，只覆盖选定的 CWE 家族，扩展到其他弱点需要额外手工工作。
- **未来改进方向**：论文指出需加强 Stage 2 义务执行、提高 CWE 匹配召回率、扩展本体和探索白盒安全评估。
