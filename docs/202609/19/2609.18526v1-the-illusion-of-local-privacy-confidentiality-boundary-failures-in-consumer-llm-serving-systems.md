## 摘要
在本地运行大语言模型（LLM）通常被认为比云端托管推理更私密，因为用户提示词保留在设备上。我们探究仅将推理保留在本地是否就足以保证这些提示词的机密性。我们的结果表明并非如此：提示词机密性还取决于周边服务软件在推理之前、期间和之后如何处理提示词数据。我们考察了消费级本地LLM服务系统中提示词机密性可能失效的四个边界：模型加载、运行时内存、包装器级持久化以及服务接口。为研究这些边界，我们开发了 LLAnalyzer，一个分别测试每个边界并将观察到的失效追溯到相应软件组件的测量框架。将 LLAnalyzer 应用于四个开放权重模型家族和两个消费级部署平台，我们发现各边界的行为差异显著。在超过1200万次执行的24小时AFL++测试中，我们在所探索的状态空间内未观察到解析器崩溃或成功的畸形GGUF加载。运行时内存则呈现不同情况：我们在推理后恢复了提示词，因为分配器管理的内存中存在多个明文表示，而清理措施减少了这种残留但并未将其消除。我们还发现消费级包装器会通过明文持久化延长提示词的生命周期。在服务边界，我们发现 llama.cpp 中一个此前未记录的授权缺陷，该缺陷允许一个已认证客户端恢复另一个租户已保存的对话状态；该攻击在200/200次受控试验中均成功。另外，共享提示前缀缓存暴露了一个远程时序侧信道，在广域网条件下仍可区分。我们认为本地LLM系统需要对提示词生命周期、持久存储和租户隔离提供明确保证。

## Abstract
Running large language models (LLMs) locally is often considered more private than cloud-hosted inference because user prompts remain on the device. We ask whether keeping inference local is, by itself, sufficient to keep those prompts confidential. Our results show that it is not: prompt confidentiality also depends on how the surrounding serving software handles prompt data before, during, and after inference. We examine four boundaries at which prompt confidentiality can fail in consumer local-LLM serving systems: model loading, runtime memory, wrapper-level persistence, and the serving interface. To study these boundaries, we develop LLAnalyzer, a measurement framework that tests each boundary separately and traces observed failures to the responsible software component. Applying LLAnalyzer to four open-weight model families and two consumer deployment platforms, we find markedly different behaviour across boundaries. In a 24-hour AFL++ campaign with more than 12 million executions, we observe no parser crashes or successful malformed GGUF loads within the explored state space. Runtime memory tells a different story: we recover prompts after inference because multiple plaintext representations survive in allocator-managed memory, and sanitisation reduces this residue without eliminating it. We also find that consumer wrappers can extend prompt lifetime through plaintext persistence. At the serving boundary, we uncover a previously undocumented authorization flaw in llama.cpp that allows one authenticated client to restore another tenant's saved conversation state; the attack succeeds in 200/200 controlled trials. Separately, shared prompt-prefix caching exposes a remote timing oracle that remains distinguishable under WAN conditions. We argue that local LLM systems need explicit guarantees for prompt lifetime, persistent storage, and tenant isolation.

## 2. 论文提出的方法论

- **核心思想：边界导向的机密性框架**
  - 不把本地部署视为单一可信环境，而是将提示词在服务栈中的生命周期分解为四个独立边界：
    1. **完整性边界（Integrity Boundary）**：模型加载与 GGUF 解析，防止恶意模型文件破坏可信执行。
    2. **生命周期边界（Lifetime Boundary）**：运行时内存中提示词明文在推理结束后是否仍可恢复。
    3. **持久化边界（Persistence Boundary）**：包装器应用是否将提示词写入持久存储。
    4. **隔离边界（Isolation Boundary）**：多个客户端共享同一服务进程时，服务接口是否保持租户状态隔离。
- **关键技术细节：LLAnalyzer 测量框架**
  - 每个边界实验遵循统一的五步流程：
    1. 陈述安全目标；
    2. 选择对应威胁模型（A1 本地进程、A2 网络客户端、A3 恶意模型提供者）；
    3. 在受控配置下测试目标边界；
    4. 获取边界特定证据；
    5. 用证据检验安全目标。
  - **UUID 金丝雀（canary）机制**：为每个推理请求生成 122 位随机 UUIDv4，嵌入提示词（`CANARY:<uuid>`），通过精确匹配将后续恢复的明文副本归因到原始请求，避免偶然碰撞。

## 6. 论文的主要结论与发现

- **完整性边界**：在测试范围内未发现 GGUF 解析器绕过、崩溃或内存安全违规；所有结构化畸形文件均被拒绝，模糊测试无异常。
- **生命周期边界**：
  - 推理完成后，可从进程内存恢复多个提示词明文副本（每租户 13–14 个）；12 个顺序租户执行后，11 个租户的提示仍可恢复，约 10.8 MB 明文。
  - 机制：`std::string` 容量增长、JSON 解析/模板扩展等瞬态对象、分配器内存重用共同导致残留。
  - 代码级清洗可减少约 29% 副本数和 69% 明文体积，但仍未恢复机密性；KV-cache 清零带来的延迟开销 <0.5%。
  - GPU 部分卸载（CUDA offloading）不消除主机内存残留；进程终止后未检测到金丝雀。
- **持久化边界**：
  - LM Studio 默认配置下，提示词明文被写入 wrapper 管理的日志（`logSensitiveData` 开启），且可在数日后恢复；禁用该设置后消失。
  - Ollama 在测试配置下未发现提示词明文持久化；网络隔离实验未观察到外部传输。
- **隔离边界**：
  - 发现 llama.cpp 中**此前未记录的授权缺陷**：一个已认证客户端可恢复另一个租户的已保存对话状态；200/200 次受控试验成功。
  - 恢复状态后模型续写在 126/200 次（63%）中复现受害者秘密，但这一比例受模型影响（Gemma/Qwen 50/50，Nemotron 25/50，Phi-4 1/50）。
  - 共享前缀缓存构成远程时序侧信道：缓存与非缓存前缀的 TTFT 完全可分（AUC = 1.000）。
- **总体结论**：本地执行不等于提示词机密性；需要跨模型加载、运行时生命周期、持久存储和租户隔离的显式保证。

## 7. 优点

- **框架化分解**：将复杂的本地 LLM 隐私问题拆分为四个可独立测量的边界，使失败可归因到具体软件组件，而非笼统地归咎“本地部署不安全”。
- **高可归因性的金丝雀方法**：使用 122 位随机 UUID 嵌入提示词，能确定性地将泄露副本与原始请求关联，避免误报。
- **多边界、多方法整合**：模糊测试、内存取证、文件分析、协议实验和时序分析被统一在同一实验逻辑下。
- **负结果与正向对照并重**：报告了模糊测试的负结果并明确其边界，同时对缓解措施做了严格效果评估。
- **实验透明度和可复现性**：提供 SHA-256 校验、固定版本、开放科学材料和伦理说明，避免对真实用户或公共系统进行攻击。

## 8. 不足与局限

- **环境单一**：所有实验在单台 Ubuntu 工作站、特定 glibc/分配器配置、固定软件版本下进行，结果可能不适用于其他操作系统、硬件或驱动组合。
- **模型和平台覆盖有限**：仅四个模型家族、两个 wrapper、一个核心推理引擎版本；未测试所有 GGUF 量化类型或不同服务架构（如 vLLM、SGLang 的具体部署）。
- **模糊测试的负结果边界**：尽管执行了 1.2×10⁷ 次，仍只探索了有限输入空间，不能证明 GGUF 解析器普遍安全。
- **清洗缓解不彻底**：论文自己指出，清洗后租户级别机密性未恢复，说明覆盖所有提示生命周期的方案尚未实现；这限制了“可缓解”结论的强度。
- **GPU 实验范围窄**：仅在一个模型（Qwen3.5-9B）上使用部分 CUDA 卸载，未验证完全卸载或其他 GPU 服务架构的差异。
- **统计与效果解释**：时序侧信道 AUC=1.000 来自受控本地/WAN 条件下样本，未在真实网络负载、噪声或不同部署配置下验证，可能高估实际可区分性。
- **未研究物理内存擦除**：进程终止后未检测到金丝雀，但未确认底层物理页面是否被覆盖，不能排除冷启动攻击等更深层风险。
- **持久化实验仅检查了特定 artifacts**：可能遗漏其他未纳入采集过程的隐藏存储点，负结果不能证明绝对不持久化。
