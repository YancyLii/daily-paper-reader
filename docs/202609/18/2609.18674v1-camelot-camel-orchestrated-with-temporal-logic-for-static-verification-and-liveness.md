## 摘要
基于大语言模型（LLM）的智能体生成并执行多步骤计划，调用可访问私有数据或执行命令的外部工具。在这种设定下，安全性是计划所生成的整个执行过程的属性，而非仅任何单一步骤的属性。计划本身是记录工具调用、控制流和数据依赖关系的关键工件。我们提出 CaMeLoT，作为 CaMeL 的补充；CaMeL 是现有的一种针对工具使用型 LLM 智能体中提示注入的防御方法。CaMeLoT 通过添加静态验证层来扩展 CaMeL，在调用任何工具之前检查智能体的计划。CaMeLoT 将生成的计划转换为有限状态迁移系统，并用工具调用、来源追踪和污点信息对其进行标注，随后使用 nuXmv 模型检验器依据以 CTL 表达的时序策略对其进行检验。由于验证发生在执行之前，不安全计划无需消耗 LLM 调用或工具调用即可被拒绝，从而节省运行时可能耗费的 token，并避免回滚变更或拆除临时沙箱。当验证失败时，模型检验器会返回反例，为智能体修复计划提供反馈。我们在源自 AgentDojo 基准、SOC 工作流和提示提取实验的策略上评估 CaMeLoT，结果表明它能在执行前验证广泛的时序属性类别，同时保留 CaMeL 可运行时检查的覆盖范围。

## Abstract
LLM-based agents generate and execute multi-step plans that invoke external tools which can access private data or execute commands. In this setting, security is a property of the entire execution that a plan creates, not just any single step. The plan itself is a critical artefact that captures the tool calls, control flow, and data dependencies. We present CaMeLoT, a complement to CaMeL, an existing defence against prompt injection in tool-using LLM agents. CaMeLoT extends CaMeL by adding a static verification layer that checks an agent's plan before any tool is invoked. CaMeLoT translates a generated plan into a finite-state transition system, labels it with tool calls, provenance and taint information, and checks it against temporal policies expressed in CTL using the nuXmv model checker. Because verification happens before execution, unsafe plans are rejected without using LLM calls or tool calls, saving tokens that runtime could have cost, as well as the need to unwind changes or teardown temporary sandboxes. When a verification fails, the model checker returns a counterexample to give feedback to the agent to repair the plan. We evaluate CaMeLoT on policies derived from the AgentDojo benchmark, SOC workflows, and prompt-extraction experiments, showing that it verifies a broad class of temporal properties before execution while preserving CaMeL's runtime-checkable coverage.

- **整体含义**：论文提出 **CaMeLoT**，作为 CaMeL 的互补扩展，在**计划生成之后、任何工具执行之前**引入静态形式验证层。它将 LLM 生成的受限 Python 计划转换为有限状态迁移系统，用 CTL（计算树逻辑）表达安全与任务属性，并通过 nuXmv 模型检验器进行验证。若验证失败，则利用反例指导 LLM 修复计划。这样可以在资源浪费发生之前拒绝不安全计划，同时保留 CaMeL 的运行时动态能力检查，形成“静态 + 动态”的混合防御框架。

## 2. 论文提出的方法论

### 2.1 总体架构
- CaMeLoT 在 CaMeL 的“计划生成 → 执行”流程中插入验证阶段，如图 1 所示：
  - 用户查询 → P-LLM 生成受限 Python 计划 → **CaMeLoT 静态验证** → 验证通过则交给 CaMeL 运行时执行；验证失败则提取反例，生成修复提示，反馈给 P-LLM 重新生成计划，直到通过或修复预算耗尽。
- 验证基于 **CTL**（计算树逻辑）与 **nuXmv** 模型检验器。

### 2.2 计划到有限状态机的转换
- 提取 Python 计划的**抽象语法树（AST）**，识别四类控制流区域：
  - `TOOL CALL`：工具函数调用。
  - `ASSIGNMENT`：纯计算赋值。
  - `CONDITIONAL`：if/else 分支。
  - `LOOP`：循环，用**非确定性选择**表示“继续迭代或退出”，以保证有限状态空间（过度近似）。
- 每个区域映射为小型状态机片段，组合成整体有限状态机 \( M = (S, s_0, \Delta, \Sigma, L) \)，其中：
  - \( S \) 是状态集，\( s_0 \) 是初始状态，\( \Delta \) 是转移关系，\( \Sigma \) 是状态变量更新效果，\( L \) 是原子命题标记函数。
- 状态机中记录工具调用、参数、目标变量、来源（provenance）和污点（taint）信息。

### 2.3 污点与溯源建模
- 变量来源映射 \( prov: Var \to \{trusted, user, untrusted, qllm\} \)，并按特权格 `trusted < user < untrusted < qllm` 排序。
- 来源标注规则：Q-LLM 输出 → `qllm`；外部工具输出 → `untrusted`；字面量 → `trusted`；用户查询参数 → `user`。派生值取依赖项的最大来源（保守污点传播）。
- 保守静态抽象：任何在运行时无法判定的、条件信任的、非信任来源的值均被标记为 `tainted`，以确保静态验证不会错误地认为不确定数据是安全的。

### 2.4 CTL 策略表达
- 安全策略以 CTL 公式形式编写，支持多种常见模式，例如：
  - **参数溯源**：`AG(call_remove_user → user_trusted)`
  - **污点预防**：`AG(call_send_money → ¬(recipient_tainted ∨ amount_tainted))`
  - **时序顺序**：`AG(host_from_qllm → A[¬call_isolate_host U call_confirm_host])`
  - **活性**：`AF(done)`
- 每条策略附带 Sigma 风格的元数据（名称、ID、状态、作者、日期、描述、级别）。

### 2.5 任务属性提取
- 可选阶段从用户提示中提取任务级需求，转换为 CTL 公式。
- **刻意限制 LLM 不直接生成 CTL**，而是让 LLM 提议一种“类型化义务”（typed obligations），再由可信代码进行**接地（grounding）**和编译为 CTL。
- 义务语言包括：存在性、全路径存在性、优先级、直到、响应、使能可达性、缺席后、下一步禁止、副作用允许列表、原子要求等十类模板（表 7）。
- 接地步骤会拒绝未知工具、未知原子或格式错误的义务，保证生成的 CTL 语法有效且标识符有界。

### 2.6 nuXmv 模型生成与验证循环
- 将控制流图转换为 nuXmv 模型，包含有限程序计数器、布尔安全命题（工具调用指示器、参数污点标志、来源标志、历史谓词）。
- 顺序语句产生确定性转移；条件产生分支转移；循环产生非确定性转移。
- 在调用 nuXmv 前，按域过滤策略集：仅选择计划中出现的工具或命题相关的策略。
- 验证通过：计划交给 CaMeL 执行。
- 验证失败：nuXmv 返回反例踪迹，CaMeLoT 将其转换为自然语言反馈（包含违反的属性、执行路径、可能位置、违规类型），提示 P-LLM 修复计划，然后重新验证。该过程类似 CEGAR（反例引导抽象精化）。

- **静态验证有效覆盖 CaMeL**：在 AgentDojo 上，CaMeLoT 能静态覆盖 22/28 条 CaMeL 安全策略；在无副作用函数的输出标记上覆盖 24/46。在 75 个成功测试中，两者在 59 个案例上决策一致（均有通过或阻止），16 个分歧主要源于 CaMeL 的运行时属性（如读者集）。
- **CaMeLoT 能表达并验证超越 CaMeL 的属性**：在 SOC 场景的 7 条 CTL 属性中，CaMeLoT 捕获了全部 7 个不安全计划，而简化 CaMeL 仅捕获了一个污点类违规（S7）。P-LLM 生成的计划测试中，CaMeLoT 捕获所有 4 个不良计划，CaMeL 一个也未捕获。
- **任务级属性可自动提取**：
  - 提取准确率：97 个任务中，87.6% 精确匹配必需副作用集合，90.7% 忠实匹配；F1 为 0.86。
  - 所有提议义务均通过词汇表和接地验证（100% 词汇表准确、100% 接地存活）。
  - 类型化管道在 97/97 任务中保持干净，而直接 CTL 生成在不同模型之间存在较多格式错误和未接地标识符，证明了架构设计的必要性。
  - 提取的 CTL 在 20 个受控案例中全部阻止违规计划、放行正确计划，并与手写 CTL 完全一致。
- **资源节省**：静态验证在计划执行前拒绝不安全计划，避免了运行时才失败的 LLM 调用、工具调用和 token 消耗成本。

## 7. 优点

- **神经符号融合**：将形式方法（CTL 模型检验）与 LLM 计划生成结合，提供了确定性安全保证，弥补了纯概率防御的不足。
- **静态 + 动态互补**：保留 CaMeL 的运行时能力检查的同时，新增执行前验证层，形成混合防线；既能检查时序属性，又不放弃动态能力/读者集等运行时决策。
- **反例引导修复**：利用 nuXmv 反例构造修复提示，使 LLM 能够针对性地调整计划，而不是重新盲目生成；类似 CEGAR 思想在智能体安全中的创新应用。
- **保守的污点抽象**：对不确定数据一律标记为污点，避免静态验证错误放行，保证安全性优先。
- **可信编译路径**：LLM 不直接生成 CTL，而是通过类型化义务 + 可信代码编译，避免了 LLM 生成语法错误或未接地公式的风险，增强了系统可靠性和跨模型一致性。
- **任务级属性提取**：不仅验证安全策略，还能从用户提示中提取任务完成义务，防止提示注入导致代理偏离用户意图（如跳过步骤、静默失败）。
- **基准与场景贴近实际**：采用 AgentDojo 和 SOC 工作流，展示了在现实安全场景中的应用潜力。

## 8. 不足与局限

- **过度抽象导致误报**：循环用非确定性选择近似，条件和循环体细节被忽略，可能产生假阳性，阻止某些安全计划；这可能导致不必要的修复或令牌浪费。
- **工具调用黑盒假设**：当前将工具调用视为黑盒，未利用工具的前置/后置条件（如 Hoare 风格规范），限制了可验证属性的丰富度。
- **静态信息有限**：读写者（Readers）能力、运行时动态能力、条件信任等无法静态判定，留给 CaMeL 运行时处理；CaMeLoT 的污点抽象可能过于保守（过度阻止）或不足（未建模保密性）。
- **实验覆盖有限**：仅使用 AgentDojo 四个套件和简化 SOC 场景，未在更多样的真实部署环境中测试；E3 案例数仅有 20 个，规模偏小。
- **模型单一**：LLM 相关实验仅使用 `claude-haiku-4-5-20251001`，未评估其他模型（如 GPT 系列、不同参数规模）对提取准确率和计划生成质量的影响。
- **未提供资源开销数据**：论文未报告验证时间、内存占用、token 节省量的具体测量，难以量化实际收益。
- **基线简化**：SOC 实验中对比的 CaMeL 是简化版，只跟踪污点，可能低估 CaMeL 的潜在表达能力，削弱了对比的说服力。
- **提示提取泛化性未知**：义务语言模板固定，可能无法覆盖复杂或新颖的用户需求；提取准确率在 Banking 套件上仅为 75%，存在改进空间。
- **计划修复未深入评估**：论文主要展示验证和提取能力，对反例引导修复的成功率、修复迭代次数、修复后计划质量等未进行系统实验。
- **潜在偏差风险**：任务属性提取和 SOC 计划生成可能受到提示设计影响，未进行多提示或多模型重复实验来评估稳健性。
