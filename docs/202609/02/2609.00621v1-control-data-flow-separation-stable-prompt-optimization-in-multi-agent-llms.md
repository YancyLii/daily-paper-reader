## 摘要
提示优化能够改进多智能体LLM系统，但被优化的提示通常承担两种相互纠缠的角色：生成任务相关内容，以及指定执行关键协议（例如消息路由、输出格式和终止信号），底层代码依赖于这些协议。因此，旨在改进内容生成的提示编辑可能无意中破坏协议，导致整个智能体流水线失败。我们的关键观察是，这两种角色具有不同的表示形式：执行协议通常是结构化的，而任务相关内容通常以非结构化语言表达。基于此，我们提出控制-数据流分离，其中执行关键的控制被表示为经过类型检查和验证的程序对象，而任务相关语言则保留为可优化的数据流用于智能体通信。该设计使优化器能够改进多智能体行为，而不会将路由或格式接口暴露给提示漂移。在合成推理、协作评审生成和保险评级工作流中，我们的框架实证实现了100%的最终协议有效性，同时持续提升任务性能。

## Abstract
Prompt optimization can improve multi-agent LLM systems, but the prompts being optimized often serve two entangled roles: generating task-relevant content and specifying execution-critical protocols, such as message routing, output formatting, and termination signals, on which the underlying code relies. As a result, a prompt edit intended to improve content generation can inadvertently corrupt the protocol and cause the entire agent pipeline to fail. Our key observation is that these two roles have different representations: execution protocols are typically structured, while task-relevant content is usually expressed in unstructured language. Based on this, we propose control-data flow separation, where execution-critical control is represented as typed, validated program objects, while task-relevant language remains the optimizable data flow for agent communication. This design allows optimizers to improve multi-agent behavior without exposing the routing or formatting interface to prompt drift. Across synthetic reasoning, collaborative review generation, and insurance rating workflows, our framework empirically achieves 100% eventual protocol validity while consistently improving task performance.

## 1. 论文的核心问题与整体含义

- **问题背景**：多智能体大语言模型（LLM）系统中，每个智能体的行为由提示（prompt）定义，提示往往同时承担两种角色：
  - **数据流角色**：生成任务相关内容，如解释、摘要、评论等；
  - **控制流角色**：指定执行关键协议，如消息路由、输出格式、终止信号等，底层程序代码依赖这些协议。
- **核心矛盾**：提示优化（如 TextGrad、DSPy 等）将提示视为可编辑参数，但一次旨在提升内容质量的编辑可能无意中破坏控制协议，导致解析失败、路由到不存在的智能体、程序崩溃等灾难性失效，而非仅仅答案质量下降。
- **关键观察**：两类角色的表示形式不同——执行协议通常是结构化的（离散动作、路由目标、终止信号等，被代码解析），而任务相关内容通常是非结构化自然语言（由其他智能体和优化器消费）。
- **整体含义**：论文提出“控制-数据流分离”框架，将执行关键的控制信息与可优化的数据信息解耦，使得提示优化可以在不破坏底层执行协议的前提下稳定进行。

## 2. 论文提出的方法论

### 2.1 核心思想：控制-数据流分离

- 每个智能体输出不再是一个无差别的字符串，而是分为两个通道：
  - **控制通道（control channel）**：`c_t^i`，类型化、经过验证的程序对象（如 Python dataclass 或 Pydantic 模型），包含路由、终止等执行决策字段，由程序控制器消费。
  - **数据通道（data channel）**：`m_t^i`，自由文本，承载任务相关内容，由其他智能体和优化器消费，不参与执行决策。
- 控制器**仅根据控制通道**做路由、终止等决策，绝不解析数据通道来决策；优化器**只能修改数据通道对应的提示**，不能修改控制模式（schema）或验证逻辑。

### 2.2 关键技术与算法流程

- **控制模式（control schema）**：每个智能体关联一个 schema `S_i`，定义控制字段名称、类型和取值范围。字段可以是 `Literal["w1","w2","w3"]` 这类封闭集合，保证合法值有限。
- **冻结的 schema 脚手架**：框架根据 schema 自动生成提示脚手架（如要求输出符合 JSON 格式的控制块），存放在**优化器不可见、不可修改的冻结槽位**中。
- **运行时验证与重试**：LLM 响应先被解析为候选控制对象 `(ĉ_t^i, m̂_t^i)`，`ĉ_t^i` 必须通过 schema 验证；失败时触发有限次重试，仍失败则回退到默认有效控制对象或作为受控失败退出循环。**无效控制对象永远不会被当作有效状态更新**。
- **优化器限制**：优化器可以编辑数据流提示，改进智能体的策略（如选择哪个路由、何时停止），但不能修改控制接口本身（schema、字段值、验证逻辑）。
- **协议稳定性保证**（Lemma 1）：在满足三个条件（C1 路由函数仅接受类型化控制对象；C2 schema 脚手架冻结；C3 解析/验证失败有重试或回退机制）下，对于任意优化器选择的提示和任意输入，执行轨迹中不会出现未处理的解析、验证或路由违规。
- **开发者接口**：实现为 Python 库 `cdsep`，使用 dataclass 定义控制 schema，路由函数签名类似 `route(ControlType) -> NextAction`，从而将控制-数据分离变成可执行的程序接口。

## 3. 实验设计

### 3.1 数据集与场景

论文在四个难度递增的场景上评估：

1. **BBH（BIG-Bench Hard 子集）**：单智能体推理任务，选取四个子任务：逻辑演绎（多选字母）、跟踪打乱物体（多选字母）、因果判断（Yes/No）、单词排序（自由短字符串）。每个子任务 25 个训练样本、25 个测试样本。
2. **MARG 评审生成**：多智能体系统（leader + 3 workers），输入 ICLR 论文（来自 ARIES 语料库），输出一组评审意见（每个意见一个实质要点）。使用 LLM-as-judge 计算对齐 Jaccard 相似度。
3. **合成保险承保**：三智能体顺序链（`extractor → rater → aggregator`），输入模拟经纪人风格的医疗摘要，输出 10 级评级桶（含 `decline/postpone`），有确定性 ground truth。
4. **行业验证的合成承保**：同样的三智能体管线，但使用行业伙伴提供的 91 条合成医疗摘要中的 20 条分层测试案例，输出 15 级评级桶。该场景额外插入 Python 端章节查找工具，将选中的章节 markdown 注入 rater 输入。

### 3.2 对比方法

- **Fixed prompts**：手动编写的提示，不进行优化。
- **Naive TextGrad**：直接应用文本梯度优化，不进行控制-数据分离。
- **DSPy（无编译）**、**DSPy + BootstrapFewShot**、**DSPy + MIPROv2**。
- **Partner-Fixed**（仅行业验证承保任务）：使用行业伙伴提供的系统提示作为校准参考。

所有方法使用相同的训练/验证/测试划分和相同的基础 LLM。

## 6. 论文的主要结论与发现

- **性能领先**：在所有四个任务上，Ours 取得最高任务得分（BBH 78.3% vs 最佳 DSPy 74.3%；MARG Jaccard 44.4 vs 43.2；合成承保 50.0 vs 47.8；行业承保 36.7 vs 31.7 Partner-Fixed 和 23.3 最佳 DSPy）。
- **稳定性**：Ours 在所有场景下实现 100% 最终协议有效性；Naive TextGrad 在高路由复杂度任务上崩溃（MARG 稳定性 0%，行业承保 56.7%），DSPy 部分变体原始 schema 有效性下降（如行业承保中 BootstrapFewShot 和 MIPROv2 降到 83.3%）。
- **消融发现**：
  - Schema 脚手架是稳定性的主要来源（Naive 到 Schema-only，MARG 稳定性从 0% 升至 100%）。
  - 重试机制提供边际可靠性提升。
  - **每示例反馈**是性能提升的主要驱动力（同一预算下，Jaccard 从 26.9% 升至 38.0%，合成承保准确率从 37.8% 升至 51.1%）。
- **跨 LLM 鲁棒性**：在 OpenAI、Anthropic、Google 三个家族上，Ours 均保持 100% 稳定性，而 Naive 均为 0%。

## 7. 优点

- **优雅的设计原则**：将软件工程中“控制与数据分离”的思想引入 LLM 多智能体系统，针对性强，解决了提示优化中的协议漂移这一实际痛点。
- **形式化保证**：提供 Lemma 1 协议稳定性证明，明确界定框架能保证什么（执行不崩溃）和不能保证什么（语义正确性）。
- **可执行且轻量**：实现为 `cdsep` 库，开发者接口简洁（示例仅需少量代码），无需修改底层 LLM 或引入额外训练。
- **全面的实验评估**：覆盖单智能体/多智能体、合成/行业数据、三种 LLM 家族，并包含消融和定性分析，证据链完整。
- **可组合性**：方法可与现有优化器（TextGrad、DSPy）和约束生成技术（如 structured output）互补。

## 8. 不足与局限

- **稳定性 ≠ 正确性**：框架只保证协议不崩溃，不保证输出内容语义正确或事实准确，协议有效的系统仍可能产出错误或低质量结果。
- **LLM-as-judge 偏差**：MARG 指标依赖 LLM 评判，虽然固定了评判模型，但固有偏差（位置、冗长、自我偏好等）仍可能存在。
- **固定 schema 假设**：实现假设智能体角色和控制 schema 预先声明，不支持动态智能体创建或运行时 schema 演化，限制了在某些动态系统中的应用。
- **数据集规模有限**：行业验证承保仅 20 个测试案例，BBH 子集较小，结论的统计力度和外部效度有限。
- **合成数据依赖**：部分任务使用合成数据，可能无法完全反映真实生产环境的复杂性。
- **未充分探索控制通道的语义正确性**：虽然路由合法，但智能体可能选择错误的合法路由或过早终止，这类语义层错误不在框架保护范围内。
