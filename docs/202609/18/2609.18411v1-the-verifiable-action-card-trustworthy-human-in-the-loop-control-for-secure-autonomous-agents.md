## 摘要
智能体浏览器可以在用户已认证会话下执行安全敏感操作，这使得间接提示注入和欺骗性确认界面直接威胁操作完整性。当批准提示本身可能受到不可信页面内容或模型生成文本影响时，现有的人类在环（HITL）防护措施并不足够。我们提出可验证行动卡（VAC），这是一种架构性防御，它从真实待执行的浏览器操作和可信意图来源重建批准信息，在可信浏览器镶边中带外呈现，并将批准绑定到在派发时重新验证的确切操作。VAC 结合了来源隔离、真实操作描述符、默认拒绝确认、来源感知风险门控和执行绑定。我们在一个完整的智能体浏览器中实现了 VAC，并在涵盖混淆代理攻击、环中谎言对话框伪造、间接提示注入、自适应操作替换、来源规避和合法任务的 24 个场景基准上对其进行了评估。在被评估的大语言模型中，不使用 VAC 时攻击成功率在 68% 到 100% 之间，而 VAC 在每个模型上都把攻击成功率降至 0%，合法任务完成率为 78%，误拦截率为 0%。这些结果表明，将批准建立在将要实际执行的操作之上，能提供架构性保护，防范提示级防御和传统 HITL 确认无法可靠阻止的安全失效。

## Abstract
Agentic browsers can execute security-sensitive actions under a user's authenticated session, making indirect prompt injection and deceptive confirmation interfaces a direct threat to action integrity. Existing human-in-the-loop (HITL) safeguards are insufficient when the approval prompt itself can be influenced by untrusted page content or model-generated text. We present the \emph{Verifiable Action Card} (VAC), an architectural defence that reconstructs approval information from the ground-truth pending browser action and trusted intent provenance, renders it out-of-band in the trusted browser chrome, and binds approval to the exact action re-verified at dispatch. VAC combines provenance fencing, a ground-truth action descriptor, default-deny confirmation, provenance-aware risk gating, and execution binding. We implement VAC in a complete agentic browser and evaluate it on a 24-scenario benchmark covering confused-deputy attacks, Lies-in-the-Loop dialog forging, indirect prompt injection, adaptive action substitution, provenance evasion, and legitimate tasks. Across the evaluated LLMs, attack success without VAC ranges from $68\%$ to $100\%$, whereas VAC reduces attack success to $0\%$ on every model, with $78\%$ legitimate-task completion and a $0\%$ false-block rate. These results show that grounding approval in the action that will actually execute provides architectural protection against security failures that prompt-level defences and conventional HITL confirmation cannot reliably prevent.

## 1. 论文的核心问题与整体含义

- **核心问题**：智能体浏览器（agentic browsers）在用户已认证会话下执行安全敏感操作，攻击者可通过间接提示注入（indirect prompt injection）、混淆代理（confused deputy）表单、以及“环中谎言”（Lies-in-the-Loop）等伪造确认界面的方式，使智能体在用户不知情下提交危险操作。
- **整体含义**：现有“人在环中”（HITL）防护的致命缺陷在于：批准提示本身可能由不可信页面内容或模型生成文本构造，因此用户看到的“待批准摘要”并不可信。一旦确认信息可被伪造，HITL 就失去安全价值。
- **关键洞见**：人类审批真正需要的是从**将要实际执行的操作的客观参数**（目标域、接收者、金额、文件路径等）和**可信意图来源**重建确认信息，并在页面无法触及的可信浏览器镶边（chrome）中呈现。论文正是围绕这一思想提出并验证架构性防御。

## 2. 论文提出的方法论

VAC（Verifiable Action Card）由五个组件构成，核心不变式是：

> 任何不可逆操作只有在用户批准了从其客观参数和意图来源导出、并在页面无法篡改的通道上呈现的描述之后才能执行。

### C1：意图来源隔离（Provenance fencing）
- 对模型所见文本标记来源：用户指令记为 `user-origin`，页面派生内容（DOM 提取文本、元素标签）记 `page-origin`。
- 页面内容被包裹在显式 fence 中，如 `<UNTRUSTED-PAGE-CONTENT ...>`。
- 作用不是说服模型忽略注入，而是为后续硬性风险门控提供可机械判定的来源信号。

### C2：地面真值操作描述符（Ground-truth action descriptor）
- 在执行不可逆操作前，直接用浏览器 DOM 解析被点击元素及其所在表单：
  - 动词（verb）、提交方法/目标域名、接收者（`to/email/iban/address` 字段或邮件格式值）、金额、上传文件路径、元素可访问名称。
- 描述符从实际执行器将要操作的元素中读取，而非页面标签或模型摘要。例如，按钮标签是“Save draft”，但描述符可能是 `verb=transfer, recipient=mule@evil.com, amount=5000`。

### C3：带外、默认拒绝确认卡片（Out-of-band, default-deny card）
- 描述符在浏览器应用的**可信 chrome 渲染进程**中渲染，而非网页内部。
- 所有值经过 HTML 转义；界面最突出控件为“拒绝”；高风险操作显示明显告警。
- 页面无法对其样式、布局、可见性进行干扰，从而消除 Lies-in-the-Loop。

### C4：来源感知风险门控（Provenance-aware risk gating）
- 用结构信号（如表单方法为 POST、提交按钮、回车提交快捷键等）判断是否为“提交操作”，不信任标签。
- 风险分析：若接收者或金额未被用户指令明确提及，或用户任务是只读但智能体尝试提交，则标记 `page-origin` 和 `elevated risk`。
- 完全由用户归属的提交可以使用轻量确认，保持风险与摩擦成比例。

### C5：执行绑定（Execution binding）
- 解决时间检查到时间使用（TOCTOU）攻击：批准时记录描述符的关键参数（接收者、金额等），在派发前重新读取并比较。
- 如果派发时参数与批准值不一致（忽略大小写/空白、数字格式归一化），则中止操作并重新拉起确认。
- 保证“所批准即所执行”。

**算法流程概览（文字描述）**：
- `BuildDescriptor`：从元素和表单读取真实目标、接收者、金额等。
- `Classify`：根据工具类型、元素类型、表单方法等判断是否为提交。
- `AssessRisk`：将描述符参数与用户指令 `I` 比较，标记 `page-origin` 或 `user-origin`、`elevated` 或 `low`。
- `Execution binding`：批准值与派发前重新读取值比对，不一致则拒绝。

## 3. 实验设计

- **场景/数据集**：自建 24 个本地网页场景，其中 13 个攻击场景、11 个合法任务。
  - 攻击类型覆盖：
    - 混淆代理表单（隐藏字段外泄、金额抬升）
    - Lies-in-the-Loop 对话框伪造（“Save draft”实际转账）
    - 间接提示注入（额外提交、删除账户）
    - 自适应攻击：后批准操作替换（TOCTOU）、相似名称接收者（`sarah@evil-exfil.com`）
  - 合法任务：联系人表单、消息发送、订阅、授权支付、发布文本等。
  - 所有场景都有服务端记录提交作为地面真值。
- **评测基准**：真实智能体浏览器（Electron/Chromium shell + Python agent + Playwright/CDP），由真实 LLM 驱动，非模拟。
- **对比方法/实验臂**：
  - **A: No-gate**：无确认，操作自动执行。
  - **B: Naive HITL**：仅根据页面标签生成摘要的确认，代表现有部署。
  - **C: VAC**：完整地面真值、来源感知、带外卡片。
  - **C–p: VAC 无来源隔离**：消融 C1，隔离来源隔离的贡献。
- **评测指标**：
  - ASR：攻击成功率（越低越好）
  - TCR：合法任务完成率（越高越好）
  - Conf.：每次合法任务的确认次数（负担）
  - FB：合法任务误拦截率
  - Attempt rate：攻击中智能体实际到达恶意提交尝试的比例

## 6. 论文的主要结论与发现

- 无 VAC 时，跨模型攻击成功率在 **68%–100%**（聚合约 78%）；使用 VAC 后**所有模型攻击成功率降至 0%**。
- VAC 下合法任务完成率为 **78%**，误拦截率 **0%**，每次合法任务平均确认次数 **0.94**。
- Naive HITL 下攻击成功率仍高达 **72%**（相对无门控 78% 只下降很小），说明现有 HITL 几乎无效。
- 攻击中，Naive HITL 在 Lies-in-the-Loop 转账场景被 100% 欺骗，而 VAC 全部阻止。
- 消融结果表明：不带来源隔离的 VAC（C–p）仍将 ASR 保持在 0%，说明**结构门控和地面真值描述符承担主要安全作用**。
- 自适应攻击（TOCTOU 替换、相似名称接收者）在无门控和 Naive HITL 下成功，但被 VAC 的执行绑定和领域级归属检查阻止。
- 结论：保护来自**系统结构**（在何处读取、在何处渲染操作信息），而非特定 LLM 的能力或安全训练。

## 7. 优点

- **架构性安全**：信任锚定在客观操作参数和可信渲染表面，不依赖 LLM 是否被诱导，跨模型表现一致。
- **解决独特缺口**：填补了“人在环中但确认信息可伪造”这一被现有推理级防御（spotlighting、structured queries、instruction hierarchy 等）忽略的问题。
- **执行绑定防 TOCTOU**：不是仅在点击前检查，而是派发前重新验证实际离开浏览器的参数，能抵御页面后批准变异。
- **带外渲染**：卡片在浏览器 chrome 中渲染，网页无法通过样式、填充、隐藏等方式篡改，性质上是 trusted path。
- **低开销、可审计**：不增加模型调用，门控是确定性规则；每个提交都有审计记录。
- **可复现性**：提供开源 artifact、场景页面、oracle、分析脚本，声称单命令即可重新生成所有结果。
- **实验设计透明**：透明 per-arm oracle 隔离界面性质，B vs C 对比干净；使用服务端副作用评分，避免智能体自报偏差。
- **与现有推理级防御互补**：那些防御降低恶意动作被尝试的概率，VAC 保证任何被尝试的提交都基于客观事实确认。

## 8. 不足与局限

- **人类模型是 oracle，非真实用户研究**：论文承认未进行受控用户研究，因此不能得出真实人类抓取率或确认疲劳结论；绝对用户表现仍有待测量。
- **来源归属是启发式**：参数与用户指令的匹配（如 `MENTIONS`）可能漏掉同义表述或错误标记合法隐式接收者，虽然误拦截率报告为 0%，但是是在简化 oracle 和有限场景下。
- **描述符保真度受执行器视图限制**：如果 DOM 在描述符构建之后、执行器读取之前发生变异，理论上有残余 TOCTOU 风险，论文未对对抗性页面变异系统评估。
- **场景和 agent 类型有限**：仅针对 DOM-first 智能体、24 个本地场景、一组受控攻击；未覆盖视觉型（screenshot-based）智能体、真实第三方网站或其他非浏览器工具。
- **某些模型本身已抗部分注入**：在无防御基线中，一些间接注入已被模型安全训练拒绝，因此 C1 来源隔离的边际价值可能被低估。
- **不解决社会工程用户指令**：如果攻击者诱导用户自己在初始指令中指定恶意接收者，参数变成用户归属，VAC 无法阻止。
- **读操作和侧信道未覆盖**：VAC 管的是提交/不可逆操作，不防止智能体在只读操作中被误导、或通过导航本身泄露信息。
- **小样本模型**：三个开源模型仅单种子试点，样本量小，统计稳健性有限；GPT-4.1 独立运行也限制直接合并比较。
- **未报告硬件资源**：无法评估推理成本或部署硬件门槛。
