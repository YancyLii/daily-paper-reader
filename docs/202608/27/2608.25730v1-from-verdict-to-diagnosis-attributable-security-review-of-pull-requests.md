## 摘要
自动化代码审查工具越来越多地被用作拉取请求（PR）的门禁，然而现有评估只衡量它们是否阻止了一个恶意变更。阻止可能由无关问题触发，而非使 PR 不安全的漏洞；修复所报告的问题后，目标缺陷仍可能被利用。我们将这种差异称为“判定-诊断（VD）差距”。我们提出 MalPR-Bench，一个基于机制的基准，包含 89 个恶意 PR 和 50 个配对的良性对照，覆盖 44 个代码仓库和八个语言家族。每个恶意案例都有预先制定的评分标准，指定目标漏洞、可接受的机制描述、所需仓库证据，以及不获得分数的偏离目标发现。审查分别按判定正确性、目标漏洞识别和证据验证进行评分；可归因的阻止要求三者全部满足。我们介绍 PRGuard，一种可归因的 PR 安全审查器，它构建候选漏洞，并使用确定性的、非执行的工具和有限检索，对照仓库证据验证其前提。在 31 个公共覆盖的留出恶意 PR 上，PRGuard 和 CodeRabbit 的阻止总数相近（22/31 对 24/31），但 PRGuard 识别出 22 个目标漏洞，而 CodeRabbit 为 16 个，相差 1.38 倍。在 14 个缺失类型案例中，两者均阻止了 9 个，但 PRGuard 识别出 9 个目标，而 CodeRabbit 仅 3 个。当所需证据位于被修改文件内时，CodeRabbit 识别出 16/24 个目标；当验证需要文件外部证据时，为 0/7。最后，PRGuard 在五个项目中发现了十二个此前未公开、有概念验证支持的漏洞。PRGuard/DeepSeek 和 CodeRabbit 均阻止了 10/12 个发现型 PR，但分别产生 10/12 和 4/12 次可归因阻止。因此，仅以判定为标准的评估可能大幅高估自动化审查的安全价值。

## Abstract
Automated code reviewers are increasingly used as gates on pull requests (PRs), yet evaluations measure whether they block a malicious change. A block may be triggered by an unrelated issue rather than the vulnerability that makes the PR unsafe; fixing the reported issue can leave the target defect exploitable. We call this discrepancy the Verdict-Diagnosis (VD) gap.   We present MalPR-Bench, a mechanism-grounded benchmark of 89 malicious PRs and 50 paired benign controls across 44 repositories and eight language families. Each malicious case has a pre-committed rubric specifying the target vulnerability, accepted mechanism descriptions, required repository evidence, and off-target findings receiving no credit. Reviews are scored separately for verdict correctness, target-vulnerability identification, and evidence validation; an attributable block requires all three. We introduce PRGuard, an attributable PR security reviewer that constructs candidate vulnerabilities and validates their premises against repository evidence using deterministic, non-executing tools and bounded retrieval.   Across 31 common-coverage held-out malicious PRs, PRGuard and CodeRabbit produce similar blocking totals (22/31 vs. 24/31), but PRGuard identifies 22 target vulnerabilities versus 16 for CodeRabbit, a 1.38x difference. On 14 absence-type cases, both block 9, while PRGuard identifies 9 targets versus 3. CodeRabbit identifies 16/24 targets when required evidence lies within touched files and 0/7 when validation requires evidence outside them. Finally, PRGuard uncovers twelve previously undisclosed, proof-of-concept-backed vulnerabilities across five projects. PRGuard/DeepSeek and CodeRabbit both block 10/12 discovery PRs, but produce 10/12 and 4/12 attributable blocks, respectively. Thus, verdict-only evaluation can substantially overstate the security value of automated review.

## 1. 论文的核心问题与整体含义

- **核心问题**：自动化代码审查工具（尤其是基于 LLM 的 PR 安全审查器）通常仅以“是否阻止恶意 PR”作为评估标准。然而，一个阻止判定可能由与真正漏洞无关的问题触发；即使修复了被报告的问题，PR 引入的实际安全缺陷仍可能被利用。
- **关键概念**：论文将这种“审查器给出正确判定，但诊断错误漏洞”的现象定义为 **判定–诊断差距（Verdict–Diagnosis gap, VD gap）**。
- **研究动机**：
  - 随着 LLM 和自主编码代理生成大量 PR，安全审查的自动化需求显著上升，但现有评估指标无法区分“正确的阻止”与“可归因的阻止”。
  - 仅凭二元判定会高估自动化审查的安全价值，因为维护者可能修复了无关问题，却留下真正的漏洞。
- **整体含义**：安全审查系统不仅要回答“是否阻止”，还要回答“该 PR 引入了什么漏洞、证据在哪里”。可归因的阻止必须同时满足 **判定正确、目标漏洞识别正确、证据验证正确** 三个条件。

## 2. 论文提出的方法论

### 2.1 MalPR-Bench 基准

- **构成**：89 个恶意 PR 和 50 个配对良性对照，覆盖 44 个仓库、8 个语言家族。
- **分层来源**：
  - **开发层**（14 个恶意 PR）：仅用于构建 PRGuard 的知识库，不进入测试。
  - **自泛化层**（19 个恶意 PR + 6 个良性对照）：来自 5 个仓库的历史挖掘，不贡献知识库。
  - **公告派生层 Pool A/Pool B**（7+7、37+37）：来自 2025 年 GitHub 安全公告，通过保留修复提交的其余变更、仅移除一个安全强制片段（Pool A）或逆转局部强制变更（Pool B）构造恶意状态；完整真实修复作为良性对照。
  - **真实发现层**（12 个恶意 PR）：PRGuard 在生产仓库中发现的、此前未公开且有 PoC 支持的漏洞，仅作为发现能力验证，不纳入公平性能比较。
- **每个恶意案例的冻结合同**：
  - 预期判定（是否应阻止）。
  - 目标漏洞定义（受影响的组件、缺失或违反的安全条件、后果）。
  - 验证要求（诊断必须以具体仓库证据支撑的安全关键前提）。
  - 评分边界（接受的等价描述和证据链，排除偏离目标发现）。
- **评分指标**：  
  - `V`：判定为阻止。  
  - `I`：正确识别目标漏洞。  
  - `E`：在 `I=1` 的基础上，提供正确的仓库事实和代码位置支撑。  
  - `A = V ∧ I ∧ E`：可归因阻止。  
- **案例属性标注**：
  - **缺陷类型**：`present-type`（验证可依赖已存在的安全相关行为）与 `absence-type`（需要证明缺少必需的安全强制，如缺失所有权检查/守卫）。
  - **证据位置**：`L0`（仅需 diff）、`L1`（需同一文件内未变更代码）、`L2a`（需被修改文件之外、通过调用/导入结构连接）、`L2b`（需被修改文件之外、通过语义对应如等价处理程序连接）。

### 2.2 PRGuard 审查器

- **核心思想**：将 PR 安全审查分解为“变更了什么 → 证据在哪里 → 是否已建立 → 应交付什么”四个阶段，分离漏洞识别与证据验证，避免早期假设支配证据采集。
- **阶段流程**：
  - **Stage 0（确定性结构采集）**：在模型推理前静态收集调用者、被调者、定义、导入、契约、数据流关系及安全覆盖对比，形成有界结构上下文包。
  - **Stage 1（变更表征）**：用模型将 diff 和结构上下文转换为安全导向的变更描述，记录受影响组件、变更前后行为、守卫/状态、敏感汇点、安全效果；对于证据不足的部分标记为 `unknown`。
  - **Path 1 · Stage 2（知识导向检索）**：使用由开发层案例构建的机制知识库（KB，21 个机制 25 个条目），将 Stage 1 的机制摘要与 KB 触发条件匹配，通过固定类型关系（`CALLER-SOURCE`、`CONSUMER-SINK`、`GUARD-DEF`、`SIBLING-ENDPOINT`）检索仓库证据。
  - **Path 2 · Stage 2.5（代码导向工作清单）**：独立于 KB，将 Stage 1 识别的组件映射到 Stage 0 路径，形成仓库内部检查目标。
  - **Stage 3（候选漏洞构建）**：根据收集到的证据构建具体候选漏洞，记录机制、攻击者能力、利用序列、可达性、影响、置信度和支持位置；保留证据不完整但合理假设的低置信度链，并记录证明缺口。
  - **Stage 4（证据验证）**：独立模型调用，对每个候选的“攻击者控制、可达性、缺失/违反的安全条件、敏感操作、后果”等前提进行验证；结果分为 `VALIDATED`、`DOWNGRADED`、`REJECTED`。验证受阻时可请求命名的有限符号定义解析，但不可进行自由搜索。
  - **判定策略**：任何 `VALIDATED` 漏洞 → `BLOCK`；仅有 `DOWNGRADED` → `COMMENT`；否则 `APPROVE`。
  - **Stage 5（审查合成）**：将结构化验证结果和预设判定转换为最终审查，必须附带可归因的仓库位置，禁止提出新漏洞或修改判定。

## 6. 主要结论与发现

- **判定–诊断差距客观存在**：
  - 在 31 个公共覆盖案例上，CodeRabbit 阻止 24/31，PRGuard/DeepSeek 阻止 22/31；但 PRGuard/DeepSeek 识别目标漏洞 22/31，CodeRabbit 仅 16/31（1.38 倍）。
  - 在 14 个 absence-type 案例中，两者均阻止 9/14，但 PRGuard/DeepSeek 识别 9 个目标，CodeRabbit 仅识别 3 个（3 倍差异）。
  - 可归因阻止：PRGuard/DeepSeek 19/31，CodeRabbit 16/31。
- **证据位置影响诊断能力**：
  - CodeRabbit 在 L0/L1 案例中识别 16/24 个目标，但在 L2a/L2b 案例中识别 0/7（Fisher 精确检验 p=0.002）。
- **真实世界漏洞发现**：
  - PRGuard 发现 12 个此前未公开、有 PoC 支持的生产漏洞，跨 5 个项目和 5 种语言，影响包括跨项目数据访问、对象级授权绕过、主机账户接管等。
  - 在发现层，PRGuard/DeepSeek 与 CodeRabbit 均阻止 10/12，但可归因阻止分别为 10/12 和 4/12。
  - 6/10 的 CodeRabbit 阻止是由偏离目标的发现触发的，修复所报告问题不一定能消除目标漏洞。
- **消融证据配置结论**：
  - 从 E0 到 E3，验证分数显著提升（GPT-5.5：6→12；DeepSeek：6→10），而识别分数提升较小（GPT-5.5：13→14；DeepSeek：10→12）。
  - 提供更多仓库上下文并未持续提升性能，表明相关证据的选择比证据量更重要。
- **无限制仓库访问不能解决所有问题**：
  - Codex-agent 双盲探针在 L1 案例上识别 3/4 个目标，但在 L2b 案例上识别 0/3，尽管部分运行给出了阻止判定；说明需要结构化的证据选择机制，而非仅凭全仓库搜索。

## 7. 优点

- **问题定义清晰且创新**：提出并形式化“判定–诊断差距”，区分判定、漏洞识别、证据验证三个层次，为安全审查评估提供了更细粒度框架。
- **基准设计严谨**：MalPR-Bench 的每个恶意案例包含预提交的评分合同，明确目标漏洞和验证要求，减少主观评分偏差；来源分层合理，兼顾受控构造与真实世界。
- **方法论系统性强**：PRGuard 将漏洞假设生成与证据验证分离，通过确定性结构采集和有界类型检索限制证据获取范围，避免自由搜索产生的噪声。
- **实验对比公平性设计**：对 CodeRabbit 作为黑盒产品仅比较最终输出，避免内部配置差异；采用盲评、人工联合裁决提高标签可靠性。
- **真实漏洞验证**：12 个 PoC 支持的未公开生产漏洞，跨多个语言和项目，并进行了协调披露，增强了方法实际价值。
- **诊断性分析有价值**：缺陷类型（presence/absence）和证据位置（L0/L1/L2a/L2b）的标注揭示了诊断失败的集中区域，为后续研究提供方向。

## 8. 不足与局限

- **对比样本规模有限**：CodeRabbit 仅运行了 31 个案例（自泛化 + 发现层），未覆盖 Pool A/B，因此跨系统结论的代表性受限。
- **发现层选择偏差**：12 个生产漏洞由 PRGuard 自身发现，其在该层上的表现存在选择偏差，论文也明确声明不能用于无偏估计。
- **消融实验的因果归因不足**：证据配置阶梯 E0–E3 同时改变多个因素，无法单独分离知识库、检索机制、阶段分离或证据闭合的贡献。
- **模型后端和评分稳定性**：模型后备阶段非确定，跨运行 `V` 在外部池中高达 25% 的变动；`I`/`E` 也有一定抖动，但论文主要基于单次运行报告，可能低估随机性影响。
- **外部效度**：基准主要由精选的公告和历史修复构造，虽然包含真实发现，但整体上对任意 PR 流的代表性有限；不能直接推广到所有仓库或语言生态。
- **CodeRabbit 作为黑盒**：无法分析其内部设计和失败原因，只能做输出级对比；且其针对不同语言/框架的性能可能波动。
- **知识库构建基于开发层**：虽然只用了 14 个开发案例，但知识库的范围可能限制了 PRGuard 对不同安全机制的泛化能力。
- **未全面披露托管模型调用细节**：未说明模型版本、温度等实现细节（部分在附录中），可能影响可复现性。
