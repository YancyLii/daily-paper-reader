## 摘要
现代 GPU 不仅需要 SIMT 式并行，还需要在计算与数据搬运之间进行软件管理的并发，才能达到最高性能。性能工程师必须考虑将工作细分到计算资源层级（线程、warp、warpgroup、block、cluster），并且在许多情况下还必须在内存层级的不同级别（寄存器、张量核心累加器、共享内存、全局内存）上使用异步张量核心和 memcpy 指令。与 CPU 中乱序执行由硬件管理并对程序员隐藏不同，GPU 通过这些异步指令将显式的指令重排暴露给软件。成熟的 GPU 编程语言通常要么提供没有安全保证的直接底层控制（例如 CUDA C++ 内联汇编或 intrinsic），要么提供更易分析的高层抽象（例如 Triton 基于 tile 的模型），这些抽象将异步指令隐藏在编译器后端，可能阻碍性能工程师通过调优关键细节来最大化性能。我们提出 Exo-GPU，一种在 CUDA 之上仅构建最小抽象的命令式低级语言。我们的核心思想是将并行与同步仅视为顺序代码上的标注，而非基本的控制流原语，从而能够验证这些构造不改变程序语义。这一设计有两方面好处：程序员可以在没有隐藏控制流或可变性的情况下对代码进行推理，同时 Exo-GPU 编译器可以验证串行-并行等价性——保证并行执行在功能上等价于其串行解释。我们使用 Exo-GPU 为 H100 GPU 编写了 GEMM kernel，采用了 wgmma、TMA 和 split-k 技术。我们的 kernel 在大规模问题上达到了理论峰值的 80% 以上，并在某些情况下超越了供应商提供的 CUBLAS 库。

## Abstract
Modern GPUs require not only SIMT-style parallelism but also software-managed concurrency between compute and data movement to reach maximum performance. Performance engineers must reason about subdividing work into the hierarchy of computation resources (threads, warps, warpgroups, blocks, clusters), and, in many cases, also must use asynchronous tensor core and memcpy instructions on different levels of the memory hierarchy (registers, tensor core accumulators, shared memory, global memory). Unlike CPUs, where out-of-order execution is managed by hardware and hidden from programmers, GPUs expose explicit instruction reordering to software through these asynchronous instructions. Well-established GPU programming languages generally offer either direct low-level control without safety guarantees (e.g., CUDA C++ inline assembly or intrinsics) or easier-to-analyze, high-level abstractions (e.g., Triton's tile-based model) that hide asynchronous instructions in the compiler backend, which may prevent performance engineers from maximizing performance by tuning critical details. We propose Exo-GPU, an imperative, low-level language that creates minimal abstraction over CUDA. Our key idea is to treat parallelism and synchronization as mere annotations on sequential code rather than as fundamental control flow primitives, enabling verification that these constructs do not alter the program semantics. The benefit is twofold: programmers can reason about code without hidden control flow or mutation, while allowing the Exo-GPU compiler to verify sequential-parallel equivalence--guaranteeing that parallel execution is functionally equivalent to its sequential interpretation. We used Exo-GPU to author GEMM kernels for the H100 GPU, using wgmma, TMA, and split-k. Our kernels achieved over 80% of theoretical peak on large problem sizes, in some cases outperforming the vendor-provided CUBLAS library.

# Exo-GPU 论文详细总结

## 1. 核心问题与研究动机

现代 GPU（如 NVIDIA H100）要达到理论峰值性能，不仅需要 SIMT 式并行，还需要程序员显式管理计算与数据搬运之间的并发。

- **异步指令暴露**：与 CPU 由硬件管理乱序执行不同，GPU 将显式指令重排暴露给软件，程序员必须手动处理异步张量核心指令（如 `wgmma`）和异步内存拷贝指令（如 TMA）的同步问题。
- **现有两类编程模型的困境**：
  - **低层方法（CUDA C++ / 内联汇编 / intrinsic）**：提供完整控制能力，但缺少安全保证，容易产生以下四类 bug：
    1. **数据流逻辑错误**：不安全的指令重排或索引错误；
    2. **指令逻辑错误**：未按硬件规范使用加速指令（如 `wgmma` 要求完整 warpgroup 统一执行）；
    3. **线程间同步错误**：两个线程访问同一内存位置却无同步约束；
    4. **线程内同步错误**：同一线程发出异步指令后，后续指令在异步指令完成前就访问了同一内存。
  - **高层方法（Triton 等基于 tile 的模型）**：更易分析，但将异步指令隐藏在编译器后端，性能工程师难以调优关键细节。作者特别指出，Triton 在 Blackwell GPU 上性能落后时不得不发明更低层的 Gluon，印证了"自动化程度过高可能阻碍极致性能"的困境。
- **目标**：提供既有 CUDA 级的控制能力、又能自动验证同步正确性的编程模型。

## 2. 方法论：核心思想与技术细节

### 2.1 核心设计理念

- **并行与同步作为顺序代码的"注解"**：程序的顺序语义是语义基线（定义用户意图），并行循环和同步语句只是指定"哪些线程执行哪些语句实例"以及"如何维护基线行为"的标注，不改变语义。
- **顺序-并行等价验证**：编译器负责验证并行解释与顺序解释在功能上等价，即不引入数据竞争或同步缺陷。

### 2.2 语言特性（GPU IR）

- **三级并行循环**：
  - `seq(lo, hi)`：顺序循环。
  - `cuda_tasks(lo, hi)`：跨 CUDA cluster 分配工作（在 sm_90 上为跨 CTA）。
  - `cuda_threads(lo, hi, unit=τ_u)`：在 cluster 内将迭代分配给线程集合，`τ_u` 指定参与线程形状（如 `cuda_warp` 为连续 32 线程组，`cuda_thread` 为单线程）。
- **分布式内存模型**：显式分布的内存分配（如寄存器分片、共享内存分片），内存归属由使用模式推断并强制一致性。例如，寄存器变量 `tmp` 若被不同线程读写而不经过 shuffle 通信，则会被一致性分析拒绝。
- **显式同步**：
  - **`Fence`**：阻塞式屏障，接收同步时间线参数（`τ_pre_s` 和 `τ_post_s`），编译器生成满足要求的最小同步指令组合（在 warp 级生成 `__syncwarp`，在 CTA 级生成 `__syncthreads`）。
  - **`Arrive` / `Await`**：分体屏障（split barrier），通过共享 barrier 变量配对，支持 `mbarrier`、`commit_group`、`cluster sync` 等机制。
  - **同步时间线（SyncTL）**：定义哪些异步操作类别（如 `cp.async`、`wgmma`、TMA）需要被等待，精确区分不同同步机制。

### 2.3 集体分析（Collective Analysis）

- 对每个程序作用域标注**集体 tiling**（`ω ∈ Ω`），描述控制变量与执行线程集合间的映射关系。
- 通过 `derive` 转换推导新的 tiling，支持形状对齐和单维细化。
- 编译为线程映射函数 `f_ω : Σ → T`，将控制环境映射到参与执行的线程集合。

### 2.4 分布式内存分析

- 静态程序一致性检查，验证所有 CUDA 作用域的变量访问与分配声明兼容。
- 收集每个使用点的三元组（细分维度、tiling、观测索引），检查线程 ownership 一致性。
- 拒绝不一致的索引、缺失/多余的线程迭代器、以及跨线程违反所有权规则的访问。

### 2.5 抽象机（Abstract Machine）验证

- GPU IR 被翻译为 **AMIR**（Abstract Machine IR），仅用于验证。
- AMIR 的关键思想是：变量不存储数值，而是存储**访问历史**（读写记录、可见性级别、线程全局 ID、异步时间线标签）。
- **可见性级别**（VL）有全序：`invisible ≺ atomic_only ≺ unordered ≺ temporally_ordered ≺ fully_ordered`。
- **记录操作**（`RecordRead` / `RecordMutate`）：将访问历史写入同步环境。
- **检查操作**（`CheckReads` / `CheckMutates` / `CheckBarrier`）：查询同步环境，验证访问是否已获得足够的可见性，否则报错。
- **同步操作**（`Fence` / `Arrive` / `Await`）：条件性地提升已有访问记录的可见性级别。`Fence` 提升可见性当且仅当"见证条件"满足（存在某全局线程的某时间线记录达到 `unordered` 以上）。
- **定性时间线（QualTL）**：区分不同类型的异步访问（如 `Sm80_cp_async_qual`、`tma_to_smem_async_qual`、`wgmma_async_smem_qual` 等），不同访问类型需要不同的硬件同步原语。

### 2.6 等价验证链

```
seq⟦p₁⟧ ≡ seq⟦p₂⟧ ≡ ... ≡ seq⟦p_N⟧ ≡ par⟦p_N⟧
```

- **Exo 重写**：复用 60+ 已验证的顺序重写规则（忽略并行/同步标注），保证数据流逻辑正确。
- **指令替换**：`replace` 重写将代码块替换为硬件指令调用，Exo 的统一化验证行为匹配，静态分析验证线程收敛要求。
- **GPU 同步检查**：通过抽象机验证最终的顺序-并行等价。

## 6. 主要结论与发现

1. **性能可行性**：Exo-GPU 能表达 H100 GEMM 达到峰值所需的所有优化（warp 专业化、cluster、TMA multicast、wgmma、commit group、mbarrier、cluster sync 等），实现超过 80% 理论峰值，部分超越 CUBLAS。
2. **安全验证的有效性**：抽象机方法能有效检测出线程间和线程内的复杂同步错误，包括异步指令与跨 CTA 同步的微妙交互。

4. **方法论可扩展**：将并行视为注解，使 Exo 的 60+ 已验证顺序重写规则可直接复用，降低了构建安全 GPU 编程语言的成本。

## 7. 优点（方法或实验亮点）

- **同兼顾控制能力与安全性**：既提供 CUDA 级显式控制，又能自动验证顺序-并行等价
- **顺序语义作为基线**：大幅简化程序推理，程序员无需担心隐藏的控制流或可变性
- **细粒度的同步建模**：定性时间线精确区分不同类型异步指令的同步需求，能检测出极微妙的错误（如本文第 2.2 节中 TMA multicast 与 wgmma 交互的案例）
- **高度可复用的重写系统**：在 Exo 框架上构建，复用已验证的顺序重写规则，降低验证成本
- **案例驱动的设计**：通过具体 bug 案例（inter-thread、intra-thread、异步交织）论证语言设计的必要性
- **验证链完整性**：从初始简单程序到最终优化并行程序的每一步都有等价性保证

## 8. 不足与局限

- **架构覆盖**：仅支持 H100（sm_90a），不支持 Blackwell 张量核心（`tcgen05`）
- **平台约束**：仅支持 CUDA C++ 和 PTX 平台
- **验证规模**：抽象机解释器只支持具体问题规模，无法静态分析任意大输入
- **验证性能**：解释器执行较慢，GEMM 4096 规模需 128 秒，阻碍迭代开发速度
- **缺少形式化证明**：代码生成基于对 NVIDIA 文档的自然语言理解，未证明相对正式 CUDA 语义的正确性
- **值敏感性缺陷**：Exo 的顺序重写无法证明某些冗余写保护是安全的（如第 8 节中 guard 消除的例子），需要人工标记为 unsafe
- **内存管理局限**：SMEM 生命周期和别名管理不够灵活，cluster 级安全要求过于保守
- **任务调度固定**：cuda_tasks 的调度顺序由编译器自动决定（轮询分配），用户无法自定义任务排序
