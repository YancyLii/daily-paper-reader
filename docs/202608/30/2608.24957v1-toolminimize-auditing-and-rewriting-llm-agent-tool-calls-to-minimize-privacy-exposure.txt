# ToolMinimize: Auditing and Rewriting LLM Agent Tool Calls to Minimize Privacy Exposure

Abstract —LLM agents routinely include privacy-sensitive data (PSD) in tool call arguments beyond what the invoked tools require, crossing trust boundaries to third-party services on every invocation. A controlled measurement on three production LLMs (GPT-4o, Claude 3.5 Sonnet, Llama-3.3-70B) shows that 81–88% of tool calls include unnecessary PSD under default prompts; explicit privacy instructions still leave 36–76% over-sharing. Existing defenses gate calls (allow/block) or label flows (information-flow control) but cannot rewrite argument values, and PII detection tools miss implicit PSD like “Memorial Sloan Kettering” (a hospital name that implies a diagnosis). We present TOOL MINIMIZE , a middleware that intercepts tool calls and rewrites their arguments to the minimum data necessary for tool functionality, combining schema-aware necessity analysis with four operations: removal, generalization, substitution, and trun-cation. Live validation on 307 tool calls across the three LLMs above reduces privacy cost by 81.2–92.0% at 100% argument-level task validity (TOST equivalence p< 0.001 at ∆=1 .0); on 25 unannotated Model Context Protocol (MCP) schemas, by 79.0% with no minimum_necessary metadata. An optional LLM content-necessity layer strips task-irrelevant PSD from otherwise-necessary free-text fields, raising live-LLM reduction to 85.1–95.6% and author-schema reduction from 71.1% to 90.9%. Median latency is 1.77 ms. 

Index Terms —privacy, LLM agents, tool use, data minimiza-tion, middleware, MCP

Across 20 everyday tasks on three production LLMs (GPT-4o, Claude 3.5 Sonnet, Llama-3.3-70B), 81–88% of tool calls contain unnecessary PSD under default system prompts (Section II); explicit privacy instructions cut this only to 36–76%, and Llama barely responds to them at all (81% →76%). Over-sharing crosses trust boundaries to third-party services with every invocation, is invisible to users, and is uncontrolled by existing frameworks. Every agent with tool-use capability [1], [2] is affected, and exposure scales linearly with the number of tool calls per task. 

a) Why existing defenses are not enough.: Allow/block gating , whether call-level (AudAgent [3], PrivacyChecker [4]) or argument-level (Progent [5], which uses JSON Schema but still emits allow/block with fallback actions), cannot rewrite argument values: a weather query with “Memorial Sloan Kettering” either proceeds and leaks the facility or is refused, losing the task. Information flow control (Fides [6], RTBAS [7], CaMeL [8]) tracks confidentiality–integrity labels at flow granularity with capability-based allow/deny; it does not perform graduated rewriting of individual fields, and its label lattices are not designed for PSD sensitivity stratification. 

PII detection tools (Presidio, AWS Comprehend) are token-level pattern matchers that miss implicit PSD (“Memorial Sloan Kettering” is not a PII pattern but implies cancer) and are schema-unaware. No existing system performs schema-aware, argument-level data minimization by rewriting tool ©2026 IEEE arXiv:2608.24957v1 [cs.CR] 25 Aug 2026 call fields while preserving task validity , and none define a quantitative privacy cost metric for tool call exposure. 

b) Contributions.: We present T OOL MINIMIZE , a mid-dleware that intercepts LLM agent tool calls before execution, classifies PSD in their arguments, computes a quantitative privacy cost, and rewrites arguments to the minimum nec-essary data. It sits between the agent and the tool without changes to the LLM, framework, or tools. Over-sharing is an inference-time phenomenon: the helpfulness objective pushes the LLM to include all context in tool arguments regardless of safety training, and our motivating study confirms that privacy prompts still leave 36–76% of calls leaking PSD. A. System Model 

An LLM agent processes a user request through five stages: user input ( V1), LLM reasoning ( V2), tool argument con-struction ( V3), tool execution ( V4), and cross-agent delegation (V5). Figure 1 illustrates the pipeline. Three trust boundaries partition it. The user–agent boundary ( V1 → V2) is trusted: the user chooses to interact. The agent–tool boundary ( V3 → V4)is semi-trusted: the agent operator selects the tool, but the tool operator is a distinct entity with its own data policies; a single request may trigger 5–20 tool calls [12]. The agent–agent boundary ( V2 → V5) has variable trust: the user consented only to the primary agent’s practices. TOOL MINIMIZE sits at the agent–tool boundary and in-tercepts every tool call after argument construction ( V3) but before execution ( V4); it requires no modifications to the LLM, framework, or tools. For highest accuracy, tool schemas should carry minimum_necessary annotations; without them, the analyzer falls back to the standard required /optional 

distinction. 

B. Adversary Model 

We consider three adversary classes. Semi-honest tool op-erators follow the protocol but log and analyze received argu-ment data for profiling, resale, or surveillance (the honest-but-curious model [12], [13], [14]). Network observers passively observe tool call payloads on the network path, including via corporate proxies or API gateways that terminate TLS [15]. 

Multi-tool aggregators correlate argument data across tool calls from the same session to reconstruct user profiles [16]. 

Out of scope. Malicious LLM providers, adversarial users, prompt injection attacks, and training data memorization are orthogonal threats addressed by complementary systems [8], [6], [17]. 

C. Privacy Threats 

We identify five privacy threats at agent–tool and agent– agent boundaries: 

C-1: Tool call over-sharing. The LLM includes PSD beyond what the tool requires; this is the most pervasive threat (Section II). Free-text fields (queries, descriptions, notes) are the primary vectors. 

C-2: Tool-level data exfiltration. A semi-honest operator extracts PSD from received arguments for profiling, resale, or surveillance. The tool functions correctly; the operator simply retains data it legitimately receives. 

C-3: Cross-tool aggregation. A multi-tool aggregator corre-lates PSD fragments across calls to reconstruct user profiles that no single call exposes [16]. 

E-1: Delegation-chain privacy degradation. Delegation pay-loads typically include the full conversational context even when the subtask requires only a narrow slice, exposing PSD to agents under weaker privacy policies [18], [16]. 

E-2: Context over-forwarding. Mirrors C-1 at the agent– agent boundary [19]: the receiving agent may itself invoke tools, creating transitive exposure chains across multiple trust boundaries. 

D. Scope and Assumptions 

TOOL MINIMIZE targets C-1 (tool call over-sharing) as its primary threat. C-1 is the most pervasive privacy threat: it affects every tool call, crosses trust boundaries with each invocation, and is invisible to users. By reducing PSD in arguments, T OOL MINIMIZE also mitigates C-2 (reducing data available for exfiltration) and limits fragments available for C-3 (cross-tool aggregation). We evaluate effectiveness against delegation threats (E-1, E-2) in Section V. We assume: (1) tools expose JSON Schema input schemas [14] (tools without schemas receive conservative defaults); (2) arguments are JSON key-value pairs; (3) the framework exposes a hook between argument construction and execution; and (4) tool success is observable from the response. Training data privacy [17], conversational disclosure, and prompt injection [8] are orthogonal threats.

D. Classifier, Analyzer, and Rewriter a) Two-stage classifier.: Stage 1 combines a Pattern-Classifier (40+ regexes covering DI, H, F, L, and additional categories) with an EntityExtractor (regex-based entity ex-traction mapped to PSD categories). Stage 2 ( SemanticClas-sifier ) catches PSD that patterns miss via sensitive facility lookup, government ID patterns, profession-based inference (e.g., “bankruptcy attorney” → F), and cross-field combina-tion detection. A base64-decoding preprocessor scans string arguments for encoded substrings; decoded spans are classi-fied and re-mapped to their source ranges, defending against simple LLM-assisted encoding evasions (Section V-D). We use deterministic regex rather than statistical NER for zero external dependencies and sub-millisecond latency. An optional spaCy NER backend (Section V-D) raises DI recall from 0.435 to 0.739 at +26 ms, which we recommend for deployments requiring higher coverage. 

b) Analyzer.: The analyzer decides each field’s dis-position in two phases. Phase 1 ( SchemaAnalyzer ) parses each tool’s JSON Schema to extract required, optional, and minimum-necessary field sets; optional PSD-bearing fields receive R EMOVE . Phase 2 ( SemanticNecessityAnalyzer ) exam-ines required fields via tool-type-specific handlers: weather fields are generalized to city level, calendar titles are re-placed with generic placeholders, search queries have identi-fiers stripped, maps queries have facility names stripped, and email fields are flagged for review. A generic handler covers 62.2% of scenarios with conservative rules: free-text fields with critical-sensitivity PSD are generalized; optional PSD fields are removed. An optional task_context parameter passes user-intent phrases that selectively retain consented PSD (unused in our benchmark). 

c) Rewriter.: Four operations correspond to analyzer dispositions: Removal (delete optional unnecessary fields), 

Generalization (coarsen values, e.g., “1275 York Ave, NY 10065” → “New York, NY”), Substitution (insert synthetic but schema-valid values like user@example.com ), and 

Truncation (round GPS, shorten ZIP+4 to ZIP-5). Three failure modes are supported: fail-closed (block the call and raise an error; default, per privacy-by-default [21]), fail-open (forward original, log incident; explicit opt-in), and fail-prompt (forward with user-confirmation flag). On initialization, the middleware flags schemas where all fields are minimum_necessary 

as suspicious, defending against semi-honest operators who might neutralize minimization via schema manipulation.

B. RQ1: Over-Sharing Is Pervasive 

Across all four LLM profiles, baseline PER averages 0.997 with 5.88 PSD items per call ( ≈3.7 unnecessary on average) and raw PCS 13.98. The near-identical exposure across profiles (range 13 .62 –14 .15 ) supports the claim that over-sharing is structural. Healthcare has the highest raw PCS (18.18); per-sonal has the highest density (7.71 items/call); even legal, the lowest-density domain (2.75 items/call), transmits unnecessary PSD in every invocation. 

a) Category distribution.: 69.4% of PSD items are in critical-sensitivity categories (DI 33.0%, H 26.6%, F 9.8%). Health-related PSD appears across all domains: agents include medical context in travel, workplace, and financial queries. Even restricting the taxonomy to the six highest-sensitivity categories (excluding I, Im, Tp, B, 5.9% of items), PER remains above 0.99, confirming that baseline over-sharing is not an artifact of broad taxonomy definitions.

A. Implications and Recommendations 

Over-sharing is structural: 81–88% of real LLM tool calls include unnecessary PSD. Prompting reduces this by at most 56% (GPT-4o) and as little as 6% (Llama). Schema-aware middleware achieves 73.6% with full task validity. The key distinction is between schema-required fields and functionally necessary content: a weather API requires a location field but needs only city-level precision. 

a) Developers.: Deploy argument-level privacy middle-ware as a standard pipeline component; annotate tool schemas with minimum_necessary fields (5–15 min per tool); default to T HIRD _P ARTY _N O_DPA for over-minimization. Tools requiring high-precision data (maps) fail without anno-tations, motivating community-maintained schema registries. 

b) Scaling beyond curated handlers.: The tool-type han-dlers (weather, calendar, maps, . . . ) are an optimization , not a requirement. A single generic handler—generalize critical-sensitivity free text, drop optional PSD fields—already covers 62.2% of scenarios, and the content-aware layer is fully tool-agnostic, judging per-item necessity from the field value and task alone. On 25 real-world MCP schemas with no 

custom handlers, T OOL MINIMIZE still reduces cost by 79.0% (Section V-D). Handlers improve precision on common tools but are not needed to onboard the long tail of APIs. 

c) Protocol designers.: MCP and other protocols cur-rently lack privacy metadata. We propose per-argument pri-vacy labels , tool-level trust declarations in server manifests, and privacy negotiation for data retention. Agent-to-agent protocols should include a required_context field; our Stage E evaluation shows T OOL MINIMIZE reduces cross-agent PCS from 12.60 to 0.00. 

B. Argument Validity vs. Task Utility 

TCR measures argument-level validity—rewritten argu-ments stay schema-valid and keep every minimum-necessary field—not end-to-end task success, and the two can diverge: generalizing a calendar event’s location or stripping a maps destination can yield a valid call that no longer serves the user’s intent. We therefore also report end-to-end execution against mock endpoints (Section V-D): 16 of 20 scenarios (80%) return functionally equivalent results, and all four failures are maps scenarios whose required addresses were re-moved absent minimum_necessary annotations—exactly the case where the over-shared field is also the task pay-load. Three mechanisms narrow this gap: the content-aware layer strips task-irrelevant PSD from within an otherwise-necessary free-text field instead of dropping the field; the optional task_context parameter retains user-consented PSD; and fail-prompt mode surfaces borderline rewrites for confirmation. Location-precise tools remain the hard case: when the destination is itself the sensitive item, routing and minimization conflict, and annotation-guided generalization (neighborhood- rather than facility-level) is the most that is safe without a user in the loop. Distinguishing the field that is structurally required from the content within it that is task-essential is the central design tension of argument-level minimization. 

C. Metric Validation 

PC is designed to rank methods by how much exposure they remove, not to predict per-call judge severity. The primary validation is therefore ordinal: across 110 perturbations of the S and E weight mappings, the method ranking is iden-tical (Kendall’s τ =1 .0); TOOL MINIMIZE is the best utility-preserving method in 100% of parameterizations. This is the property the comparison results in Section V-C actually depend on, and it holds regardless of the specific weight choice. Per-call correlation with LLM judge severity is a sec-ondary sanity check. Three LLM judges (GPT-4o, Claude Sonnet, Llama-3.3-70B) agree with each other ( ρ=0 .69 ) but rate a privacy-critical corpus near ceiling (median 4.3/5), so even a perfect metric could not produce strong rank correlation against compressed judge scores. Under schema-level N the aggregate ρ=−0.26 (p=0 .03 ), driven entirely by 18/73 messaging calls receiving PC =0 when all PSD lives in minimum_necessary fields; per-item N judged by an LLM removes the zero-variance collapse and recovers 

ρ=+0 .04 (95% CI [−0.20 , +0 .28] ). The point estimate is non-negative, which is what the metric needs given saturation. The ranking-monotonicity claim is what carries the comparison.

Ecological validity : the 99.7% baseline PER reflects a privacy-critical corpus; general use is lower. User agency : T OOL MIN -

b) Future work.: Adaptive NER backend for latency; session-level budgets [16]; CaMeL integration for joint confidentiality–integrity [8]; user-controlled minimization with preview UI; multimodal PSD detection. VII. R ELATED WORK 

a) Privacy in LLM systems.: Prior work addresses training-time memorization [17] and conversational disclo-sure [23], [22], [24]. Those adversaries extract data from the model; tool call over-sharing is the model actively sending 

data to third parties. 

b) Agent security and privacy.: AudAgent [3] auto-formalizes natural-language privacy policies via cross-LLM voting and blocks policy-violating actions, but its intervention is binary (allow/block) at the action level rather than field-level rewriting. PrivacyChecker [4] extracts the contextual-integrity (CI) five-tuple [25] per information flow and gates entire tool invocations; it reasons about attributes but does not mutate argument values, so it cannot distinguish a weather query with “New York, NY” from one with “Memorial Sloan Kettering.” Progent [5] also uses JSON Schema to express fine-grained policies over tool call arguments, but enforces via allow/block with fallback actions rather than argument-level rewriting. Das et al. [26] audit contextual privacy with detection focus. AgentPrint [27], MEXTRA [28], and Patil et al. [16] address traffic fingerprinting, memory extraction, and compositional risks, respectively. Chen et al. [29] show users systematically underestimate privacy leakage; the invisibility of tool call arguments exacerbates this. Concurrent benchmarks [9], [10], [11] corroborate over-sharing in agent pipelines. 

c) Information flow control.: Agent IFC systems track confidentiality and integrity labels at flow granularity. Fides [6] tracks both axes with capability-based allow/deny decisions; CaMeL [8] uses capabilities to block private-data exfiltration over unauthorized flows; RTBAS [7] targets both prompt injection and privacy leakage. All three enforce at flow gran-ularity rather than performing graduated rewriting (removal, generalization, truncation) of individual argument fields, and their binary tainted/clean labels cannot capture the sensitivity spectrum (an email address and a cancer diagnosis carry very different exposure risks). T OOL MINIMIZE and these systems are complementary. 

d) Data minimization and PII tools.: GDPR Art. 5(1)(c) [21] codifies minimization; Presidio and AWS Comprehend implement it via pattern+NER. These tools have three limitations for agent tool calls: (i) they miss 

implicit PSD (“Memorial Sloan Kettering” is not PII but implies cancer); (ii) they are schema-unaware ; (iii) they apply uniform redaction regardless of tool trust. GAMA [30] and DP-RAG [31], [32] handle document-level anonymization; PAPILLON [33] and Bagdasarian et al. [34] minimize at the prompt boundary; PrivWeb [35] protects DOM text for web agents. Differential privacy (DP) is a poor fit for tool arguments: format constraints (email, ISO date) preclude noise. TOOL MINIMIZE targets a complementary boundary (tool call argument egress) with schema-based necessity and graduated rewriting (Table VI). No existing system performs schema-aware, argument-level minimization by rewriting tool call fields while preserving task validity; T OOL MINIMIZE fills this gap. Integration with CaMeL or Progent for joint confidentiality–integrity is feasible (Section VI-D0b). VIII. C ONCLUSION 

Safety training cannot eliminate tool call over-sharing: the helpfulness that makes an agent useful is the same mechanism that leaks context into its tool arguments. T OOL MINIMIZE 

shows that schema-aware argument rewriting reduces privacy cost by 81.2–92.0% on 307 live tool calls from GPT-4o, Claude Sonnet, and Llama-3.3-70B, with 100% argument-level task validity (TOST p< 0.001 ). The schema-only path runs at 1.77 ms median, no LLM call required. An optional content-necessity layer that asks an LLM, per detected item, whether the value is task-essential raises live-LLM reduction to 85.1– 95.6% and author-schema reduction from 71.1% to 90.9% by catching PSD that lives inside otherwise-necessary free-text fields. Residual exposure is bounded by classifier recall (worst case 4.09 PCS/scenario, observed 0.59).
