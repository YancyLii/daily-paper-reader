## 摘要
新兴的 W3C WebMCP 提案使大语言模型智能体能够调用网页暴露的工具。然而，在多参与方的 Web 环境中，将智能体执行整合到以同源策略（SOP）为中心的浏览器安全模型中，难以为智能体可访问的工具提供充分的来源与生命周期保障，从而带来三类风险：主体归属欺骗、不受控的工具生命周期以及语义提示注入。我们提出 WebMCP-Phalanx，一种双层智能体运行时架构。其第一层提供浏览器原生信任锚，通过受密码学保护的能力凭证将每个工具绑定到其注册主体，并在工具生命周期内传播来源标签。其第二层将语义检查与特权工具使用相分离。隔离智能体（Q-LLM）不具备工具调用权限，负责检查工具元数据、输出和页面提供的内容中是否存在提示注入。经过验证的内容随后被转发给特权智能体（P-LLM）执行，而 Q-LLM 的内部状态对页面脚本保持隐藏。实证评估表明，浏览器原生所有权机制将撤销与覆盖攻击的成功率从 100% 降低到 0%。双智能体运行时阻止了工具描述中嵌入的全部 80 次提示注入尝试，并将工具返回攻击限制为 80 次中仅 2 次成功。在所有实验中，任务效用与无攻击基线在统计上无显著差异。然而，在白盒自适应攻击者场景下，基于描述的过滤可被在检查前调用的恶意工具名称绕过。这一发现促使设计调用时序门控，在所有智能体可见的工具元数据得到验证之前延迟工具调用。

## Abstract
The emerging W3C WebMCP proposal enables LLM agents to invoke tools exposed by web pages. In multi-party web environments, however, integrating agent execution into a browser security model centered on the Same-Origin Policy (SOP) leaves insufficient provenance and lifecycle guarantees for agent-accessible tools, creating three risks: subject-attribution spoofing, uncontrolled tool lifecycles, and semantic prompt injection. We propose WebMCP-Phalanx, a dual-layer agent runtime architecture. Its first layer provides a browser-native trust anchor that binds each tool to its registering principal through cryptographically protected capability credentials and propagates provenance labels throughout the tool lifecycle. Its second layer separates semantic inspection from privileged tool use. A Quarantine Agent (Q-LLM), without tool invocation authority, inspects tool metadata, outputs, and page-supplied content for prompt injection. Validated content is then forwarded to a Privileged Agent (P-LLM) for execution, while the Q-LLM's internal state remains hidden from page scripts. Empirical evaluation shows that the browser-native ownership mechanism reduces revocation and overwrite attack success from 100\% to 0\%. The dual-agent runtime blocks all 80 prompt-injection attempts embedded in tool descriptions and limits tool-return attacks to 2 successful cases out of 80. Across experiments, task utility remains statistically indistinguishable from the no-attack baseline. Under a white-box adaptive attacker, however, description-based filtering can be bypassed through malicious tool names invoked before inspection. This finding motivates a call-timing gate that delays tool invocation until all agent-visible tool metadata has been validated.

## 1. 论文的核心问题与整体含义

- **研究背景**：W3C 正在制定 WebMCP 标准，允许网页向基于大语言模型（LLM）的智能体暴露可调用的结构化工具，使智能体从“读取网页”升级为“直接执行网页提供的动作”。
- **核心问题**：浏览器安全模型以同源策略（SOP）为中心，但在多参与方网页环境中，同一源内的主站脚本、第三方广告 SDK、分析脚本之间没有明确信任边界。WebMCP 的现有设计缺乏对工具来源归属、生命周期和语义内容的可信保障，导致三类风险：
  - **主体归属欺骗**：工具列表不携带来源信息，任意同源脚本可抢占工具名、撤销他人工具或替换工具；
  - **不受控的工具生命周期**：SPA 逻辑页面切换后工具仍残留；
  - **语义提示注入**：结构上合法的工具在描述、输入模式或返回内容中嵌入操纵指令。
- **整体含义**：仅靠模型自身的安全过滤或后端语义验证无法解决协议层的结构缺陷；需要在浏览器原生层建立不可伪造的信任锚，并在智能体运行时中实现权限隔离的语义检查，形成“来源可信”与“使用可信”分离的防御体系。

## 2. 论文提出的方法论

- **总体思想**：WebMCP-Phalanx 将“来源验证”与“语义执行”严格解耦。浏览器原生层生成不可伪造的工具信任标签；多智能体运行时根据标签强制实施数据流策略，使智能体无需自行推断工具可信度。
- **第一层：浏览器原生信任锚**
  - **工具所有权机构（Tool Ownership Authority）**：将工具注册、枚举、注销等核心状态抽象到浏览器原生实现层，对页面 JavaScript 完全隔离。注册成功后签发不透明、不可伪造的能力凭证（capability handle）；撤销或覆盖工具必须出示对应凭证，从而阻止同源第三方脚本篡改他人工具。
  - **注册来源标注**：在 `tools/list` 调用时，从隔离状态中读取工具注册来源，附加防伪造的来源标签；但无法区分同源内不同脚本（结构限制）。
  - **生命周期监控器**：拦截 History API（`pushState`、`replaceState`、`popstate`），检测 SPA 逻辑页面转换，主动清除声明为 `navigation` 作用域的工具，避免工具残留。
  - **运行时观测**：异步监控外发数据通道（`fetch`、`sendBeacon`、`Image.src`）和 DOM 变异，与工具静态声明行为比较；发现偏差（如只读工具发起网络请求）立即将信任标签降级为 Red，并注入输出和后续注册表读取。
  - **数据边界机构（Data Boundary Authority）**：综合来源维度与内容维度，为每个工具生成三级信任标签：
    - **Green（可信）**：来源通过密码学验证，运行时行为符合声明，允许直接执行；
    - **Yellow（需注意）**：来源可信但声明涉及环境变更，需轻量语义验证；
    - **Red（不可信）**：来源不合法或运行时发现违规，隔离或明确阻止。
- **第二层：非对称双智能体隔离运行时**
  - **特权智能体（P-LLM）**：拥有工具调用权限，负责执行任务；
  - **隔离智能体（Q-LLM）**：无任何工具调用权限，专门检查工具元数据、返回内容等是否包含提示注入；其内部状态对页面脚本（包括同源脚本）不可见，防止攻击者观测检查过程并自适应调整输入。
  - **两个检查点**：
    - **执行前描述分析**：检查工具静态描述和输入模式，拦截注册阶段的静态提示注入；
    - **执行后返回分析**：在执行后拦截并净化返回内容，防止动态生成的恶意载荷重新进入 P-LLM 记忆。
  - **请求用户界面（RUI）**：作为最后防线，仅在 Red 级或无法确定性分类的极敏感操作时通过可信路径请求用户确认；Green/Yellow 由双智能体运行时自主处理。
- **算法/流程**：页面脚本调用 `registerTool` → 所有权机构拦截并管理状态 → 标签生成 → 多智能体运行时根据信任层级路由：Green 直接到 P-LLM，可疑内容路由到 Q-LLM 隔离沙箱评估后再决定是否放行。

## 6. 论文的主要结论与发现

- **所有权机制有效**：浏览器原生能力凭证将撤销和覆盖攻击成功率从 100% 降至 0%，所有伪造凭证尝试均被阻止；同源脚本只能修改自己注册的工具。
- **双智能体运行时显著阻断语义注入**：
  - 描述注入：L3 将 80 次攻击全部阻断（0/80），L2 只能降至 25/80；
  - 返回内容注入：L2 和 L3 均将 80 次攻击降至 2/80，残留的 2 次均由工具名称在语义检查完成前触发工具调用造成。
- **跨页面残留防御**：仅清除工具只能将攻击成功率从 80% 降至 70%，因为注入语义已残留在对话历史中；通过将信任标签生命周期扩展到工具生成的内容，并在工具清除时使历史中残留内容的标签失效，可将攻击成功率降至 0%，同时不损害正常导航任务（任务完成率 100%）。
- **名称工程与可替代性**：规则剥离在工具名称与任务高度相关时失效（L2 攻击成功率最高达 70%），而多智能体内容判断不受名称包装影响（L3 始终为 0%）；可替代性（工具能否替代原有工具功能）决定攻击可达性，而非单纯的序列刚性。
- **白盒自适应攻击限制**：当攻击者将对抗指令放在任务相关工具名称上并在检查前导致工具被调用时，描述层过滤器仍可被绕过（16 个载荷中有 15 个被绕过，重写轮次中位数为 1）；这需要名称层或调用时序门控来闭合漏洞。
- **任务效用保持**：在受保护运行时中，任务完成率与无攻击基线在统计上无显著差异（如描述通道 L3 完成 56/80 vs 无攻击基线 61/80，p=0.48）。

## 7. 优点

- **架构解耦清晰**：将来源验证（浏览器原生层）与语义执行（多智能体层）严格分离，解决多智能体防御中“可信标签从何而来”的根本问题。
- **原生信任锚设计**：能力凭证机制在浏览器层建立确定性所有权，不依赖 JavaScript 层身份，抵抗同源脚本的伪造与篡改。
- **隔离智能体设计巧妙**：Q-LLM 无工具权限且内部状态对页面脚本不可见，防止攻击者观测并自适应调整注入内容。
- **实验设计严谨**：采用四层消融、统计显著性检验、以无攻击基线锚定效用比较，并有意不阻止检测以评估检测上限，方法论上较客观。
- **暴露关键限制**：论文不仅报告成功，还系统刻画了能力凭证无法解决的“同源内主体归属”问题和白盒自适应攻击可绕过内容过滤的路径，为 WebMCP 规范改进提供了具体输入（如原生脚本来源、声明式信任拓扑、调用时序门控）。
- **针对标准制定阶段**：在 WebMCP 尚未固化时发现结构性问题，对 W3C 具有及时参考价值。

## 8. 不足与局限

- **实现为 polyfill 而非原生实现**：API 表面完整性通过预加载缓存原始内建引用来模拟，未在真实浏览器原生层实现；密码学脚本来源在 vanilla JavaScript 中结构缺失，相关结论依赖架构存在性假设，而非密码学可迁移的保证。
- **能力凭证的承载性缺陷**：凭证作为 bearer credential，存在 confused deputy 问题——注册主体若泄露句柄或暴露代其撤销工具的函数，将丧失所有权保证。
- **同源内主体归属未解决**：能力凭证无法区分同源内不同脚本，恶意脚本注册工具后同样获得合法凭证，来源维度退化；需要原生脚本来源和站点声明式信任拓扑，但本文未实现评估。
- **运行时观测非预防性**：观测是执行后检测，无法阻止首次违规的副作用；异步观测窗口内可能无法将 DOM 变异归因到具体工具，存在归因碰撞。
- **时序窗口漏洞**：工具名称可在语义检查完成前触发调用，导致返回内容注入残留 2/80 或白盒攻击绕过；需额外的名称层或调用时序门控，本文未实现。
- **白盒评估样本有限**：仅 16 个描述层载荷，结论可能受限于特定载荷集和攻击策略。
