## 摘要
间接提示注入（IPI）会在使用工具的LLM智能体所读取的内容中植入指令，诱导智能体执行有害的工具调用。最强的防御是系统级防御，利用任务条件工具筛选以防止执行恶意工具，以及信息流控制以避免使用不可信参数执行工具。然而，随着智能体能力增强，用户将更多任务委托给自动化。因此，工具执行序列和参数值越来越多地在运行时确定，仅凭用户查询无法可靠筛选，除非造成显著的效用损失。我们提出ROPE（路由来源策略强制执行），它基于一种结构化的信任概念：一个值只有在能够不可伪造地追溯到用户、用户明确指定的来源或用户自己的权威记录时，才能到达会改变状态的工具。该强制执行方式是对一组经审计的敏感工具参数进行确定性的来源检查，唯一依赖语言模型的部分仅涉及可信的用户请求，不在攻击者的影响范围内。我们的方法具有两项可证明保证：1）在轨迹的每一步，任何仅来源于攻击者可写内容的值都不会到达受来源保护的参数；2）对注入的任何改写都不会改变准入决定。我们在开放式智能体套件上对四个智能体模型进行评估，ROPE将攻击成功率控制在1.6%--2.6%，同时保留82%--100%的无防御干净效用，在效用上显著超过最先进的系统级防御，并获得相当或更好的安全性。此外，我们表明针对ROPE优化注入基本无效，而能击败先前系统级防御的长期攻击则达到零成功率。我们的代码和日志可在 https://github.com/xhOwenMa/ROPE 获取。

## Abstract
Indirect prompt injection (IPI) plants instructions in the content a tool-using LLM agent reads, steering the agent into harmful tool calls. The strongest defenses are system-level, leveraging techniques such as task-conditional tool screening to prevent execution of malicious tools, and information-flow control to avoid tool execution with untrusted parameters. However, as agents grow more capable, users delegate more to automation. Consequently, tool execution sequences and parameter values are increasingly determined at runtime and cannot be reliably screened from solely user's query without significant utility loss. We present ROPE (Routed Origin Policy Enforcement), which is anchored in a structural notion of trust: a value may reach a state-changing tool only if it traces unforgeably to the user, a source the user explicitly named, or the user's own authoritative records. Enforcement is then a deterministic origin check over an audited set of sensitive tool parameters, and the only reliance on a language model involves solely the trusted user request, out of the attacker's reach. Our approach admits two provable guarantees: 1) at every step of a trajectory, no value whose only origin is attacker-writable content reaches an origin-guarded parameter, and 2) no rewording of an injection changes an admission decision. We evaluate across four agent models on open-ended agent suites, ROPE holds attack success rate to 1.6--2.6\% while retaining 82--100\% of undefended clean utility, significantly exceeding state-of-the-art system-level defenses in utility while attaining comparable or better security. Further, we show that optimizing the injection against ROPE is largely ineffective, while long-horizon attacks that defeat prior system-level defenses achieve zero success rate. Our code and logs are available at https://github.com/xhOwenMa/ROPE .

- **核心矛盾**：随着智能体能力增强，用户越来越多地委托自动化，工具执行序列与参数值越来越依赖运行时读取的内容。固定策略或预计算计划难以兼顾安全与效用，已有系统级防御在开放基准（如 AgentDyn）上干净任务完成率大幅下降。
- **论文定位**：提出 ROPE（Routed Origin Policy Enforcement），以结构性信任来源（用户、用户指定源、用户权威记录）为基础，对敏感工具参数执行确定性来源检查，避免在强制执行回路中使用语言模型，从而在保持高效用的同时显著降低攻击成功率。

## 2. 方法论

### 2.1 核心思想

- **信任锚（Trust Anchors）**：一个值只有在能够不可伪造地追溯到以下三类来源时，才允许到达会改变状态的工具：
  - **T1**：用户的实际请求（query）；
  - **T2**：用户请求中明确引用的不可伪造运行时来源（如带签名的邮件发件人地址）；
  - **T3**：用户自己的权威记录（平台维护的用户操作日志、订单历史等）。
- **威胁模型假设**：攻击者可向智能体读取的任何非用户权威记录内容注入指令；不能观察或篡改用户查询；不能伪造不可伪造来源身份；不能写入用户权威记录；防御设计对攻击者公开。

### 2.2 ROPE 架构与流程

ROPE 包含一次离线设置和三个每任务步骤：

- **离线设置**：从工具 schema 中识别所有会改变状态的工具及其敏感参数（如收款人、URL、目标仓库、消息内容等），生成固定、可审计的敏感参数表。
- **步骤 1：路由与范围界定（仅可信输入）**：一个 LLM 调用仅读取用户请求（不读任务期间获取的内容），输出：
  - 任务的**欠指定程度**：完全指定（fully-specified）、参数开放（parameter-open）、动作开放（action-open）；
  - **范围**：用户引用的命名来源及用户逐字写出的参数值。
- **步骤 2：编译确定性策略**：根据欠指定程度，为每个敏感参数分配一个**来源标记**：
  - `CONST` / `PROMPT`：值必须与用户请求中的值/标识符完全匹配（仅 T1）；
  - `SOURCED`：额外接受来自用户命名来源的值（T1/T2）；
  - `RECORD`：额外接受用户权威记录中的值（T1/T3）；
  - `FREE`：无来源限制，仅用于合理委托的自由文本参数（如邮件正文）；
  - `DEST`：阻止写入凭据/系统目录，除非请求中明确命名路径；
  - `EXPLICIT`：不可逆操作（如删除仓库）必须由请求明确授权。
- **步骤 3：运行时确定性执行**：来源追踪器记录每个值从哪个工具、以何种结构进入智能体，不读取文本内容本身。当智能体尝试调用敏感工具时，ROPE 检查参数值是否与任务接受的来源匹配；只读工具始终放行。

### 2.3 关键机制细节

- **来源追踪器**：根据工具结果的结构划分条目：
  - 已认证身份的结果（如签名邮件）按条目标记来源，标记 T2；
  - 整块不可分割内容（文件体、网页）标记为可注入，即使请求命名该文件也不信任；
  - 权威记录工具结果标记为 T3。
- **匹配规则**：
  - 列表参数要求每个元素都可信，防止注入项混入；
  - 匹配基于**决策单元**（decision unit），如仓库名整体、邮箱地址整体、URL 主机名，不拆分匹配，防止拼接攻击（如 `attacker/victim-repo` 不匹配 `victim-repo`）。
- **路由器隔离**：防御中唯一的语言模型只处理用户请求，不在强制执行回路中读取可能被注入的内容。

### 2.4 可证明保证

- **引理 1（记录闭包）**：如果所有写入记录字段的工具参数都满足标记支配条件，则 T3 字段完整性在整个轨迹中保持。
- **命题 1（来源健全性）**：在假设 A1（来源元数据完整且匹配真实）、A2（记录完整）、A3（敏感工具枚举完整）下，任何被 ROPE 准入到来源保护参数的值都具有对 T1/T2/T3 的不可伪造追溯；即攻击者可写内容不会到达来源保护参数。
- **命题 2（改写不变性）**：注入内容的改写不会改变 ROPE 的准入决策；因路由器只读取请求，强制执行是确定性函数。

## 6. 主要结论与发现

- **安全与效用双优**：在 AgentDyn 上，ROPE 将 ASR 控制在 1.6%–2.6%，同时保留无防御干净效用的 82%–100%；显著优于所有基线。
- **基线对比**：现有系统级防御要么保持高 ASR，要么通过牺牲任务完成率降低 ASR；ROPE 是唯一处于低 ASR 且高效用区域的防御。
- **自适应攻击无效**：AutoDojo 优化器对 ROPE 的 ASR 几乎无影响（变化不超过 0.4 个百分点），验证了改写不变性；而 DRIFT 等基线的 ASR 被优化器大幅推高。
- **长期攻击零成功**：在 AgentLAB 长期分段攻击下，ROPE 在所有套件和模型上实现 ASR=0，同时维护接近无防御的 UA。
- **路由器成本可承受**：廉价路由器（如 gpt-oss-20b）在启用 clamp 后 ASR 不显著上升，效用损失有限。
- **消融**：仅固定“完全指定”或“动作开放”策略会导致效用骤降或 ASR 飙升；路由策略通过按参数放宽来源实现最优平衡。

## 7. 优点

- **确定性安全执行**：在强制回路中无 LLM 判断，减少攻击面，避免防御自身被注入操纵。
- **可证明保证**：提供来源健全性和改写不变性两个正式保证，理论基础扎实。
- **结构性信任锚**：利用平台已有的安全机制（签名、认证、用户记录）将信任扩展，避免对所有运行时内容一刀切不可信。
- **参数级策略**：根据用户请求的欠指定程度动态调整敏感参数的来源范围，兼顾安全与效用。
- **可审计默认值与 clamp**：每个敏感参数有离线默认标记；部署可将默认值作为下限，限制弱路由器的安全风险。
- **广泛评估**：4 个模型、6 个套件、11 个基线、3 类攻击、多组消融，实验较为全面。
- **失败分析透明**：对残留攻击成功和干净任务失败进行分类，说明边界，不夸大防御能力。

## 8. 不足与局限

- **非工具消息内容不受保护**：当危害仅体现在智能体对用户的文本回复中（如推荐受注入影响的酒店）时，ROPE 无法阻止。
- **自由文本/体内内容不可控**：如果危害在于已授权目的地（如用户指定的收件人）的消息正文中插入钓鱼链接，ROPE 的确定性来源规则无法限制正文内容。
- **完全委托敏感参数的盲区**：当合法值与注入值共享同一不可信来源且无法通过来源区分时（如从不可信账单读取付款 IBAN），ROPE 会拒绝合法值导致任务失败或允许攻击值。
- **依赖平台元数据与假设**：需要平台暴露值的来源元数据；假设 A1、A2、A3（来源完整、记录完整、敏感工具枚举完整）在真实部署中可能不成立，特别是若工具接口与实现脱节（如浏览工具实际触发状态更改）。
- **实验局限性**：
  - 动作开放类别样本量较小（AgentDyn n=8、AgentDojo n=6），可能导致统计不稳；
  - 论文未报告 GPU/算力细节；
  - 基准环境为模拟，与生产系统存在差距；
  - 部分评分经过人工修正，可能引入主观性。
- **路由器模型依赖**：虽然 clamp 能约束弱路由器安全性，但路由器本身的输出质量仍影响干净效用或误拒率。
- **未能处理基于意图的攻击**：保证只涉及值的来源，不保证值就是用户想要的；当合法值本身无可靠来源时，防御只能失效关闭。
