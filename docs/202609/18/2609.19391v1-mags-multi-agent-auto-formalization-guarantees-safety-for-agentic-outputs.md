## 摘要
LLM 编程智能体现在以如此规模生成复杂程序，使得彻底的人工审查愈发困难，从而增加了安全性和安保性失效的风险。常见方法（包括模糊测试、静态分析和 LLM 作为验证器）能检测许多失效，但难以覆盖所有可能的边界情况。形式化验证通过为指定性质提供机器可检查的保证来解决这一问题，但传统上需要大量手工编写规范和证明工程。我们引入了统一的多智能体框架 MAGS，该框架生成具有形式化安全保证的可执行程序，并使用 Dafny 作为可验证的中间表示，以便对安全性质进行机械检查。MAGS 将经过人工审计的 API 与安全需求形式化并冻结，将生成的代码转换为 Dafny，利用验证器反馈修复违规，并将验证后的程序编译回可执行代码。我们在 100 个 CUDA 内核、100 个终端脚本和 20 个机械臂任务上评估了 MAGS。在全部 220 个示例中，它在针对冻结规范生成具有非平凡安全保证的程序方面取得了 100% 的成功率。独立的安全和功能评估进一步显示其在所有三个领域都表现强劲，同时揭示了当自动形式化语义未能完全捕捉目标行为时会出现失败。

## Abstract
LLM coding agents now generate complex programs at a scale that makes thorough human review increasingly difficult, raising the risk of safety and security failures. Common approaches, including fuzz testing, static analysis, and LLM-as-a-Verifier, can detect many failures but struggle to cover all possible edge cases. Formal verification addresses this by providing machine-checkable guarantees over specified properties, but traditionally demands substantial manual specification and proof engineering. We introduce a unified multi-agent framework, MAGS, that generates executable programs with formal safety guarantees, using Dafny as a verification-aware intermediate representation where safety properties can be mechanically checked. MAGS formalizes and freezes human-audited APIs and safety requirements, translates generated code into Dafny, repairs violations using verifier feedback, and compiles verified programs back into executable code. We evaluate MAGS on 100 CUDA kernels, 100 terminal scripts, and 20 robotic-arm tasks. Across all 220 examples, it achieves a 100% success rate in producing programs with non-trivial safety guarantees against frozen specifications. Independent safety and functional evaluations further show strong performance across all three domains, while revealing failures when the auto-formalized semantics do not fully capture the target behavior.

## 2. 论文提出的方法论

### 2.1 核心思想

- **验证语言与执行语言分离**：程序在目标语言（CUDA、Python 等）中执行，但安全性在验证语言 Dafny 中证明。
- **一次性领域形式化 + 逐任务验证**：语义构建是一次性成本；每个领域先由智能体自动形式化 API 语义与安全要求，经人工审计和测试后冻结，后续任务无需额外人工干预。
- **多智能体闭环**：翻译、证明规划、修复、编译回目标语言均通过专用智能体完成，并用验证器反馈驱动修复。

### 2.2 语义构建阶段

- **核心逻辑基础**：每个领域从少量人类编写的逻辑基础开始，定义抽象状态与推理原语。
  - CUDA：基于分数权限的分离逻辑，支持排他写、共享读，并定义越界、数据竞争、barrier divergence 等安全性质。
  - 终端：模块特定形式系统，如用于 shell 操作的符号有限状态转换器、用于加密 API 的 CrySL、用于正则表达式的单义正则语言。
  - 机器人：运动学与控制状态语义，包括空间边界和碰撞相关安全条件。
- **自动形式化**：LLM 智能体根据官方文档扩展 API 语义；批评智能体检查忠实性、一致性、模块化。
- **审计与测试**：人工随机审计 20% 生成的语义；每个语义库用独立生成的 3 个安全探针和 3 个不安全探针测试，要求所有安全探针通过验证、所有不安全探针被拒绝。
- **冻结语义**：核心逻辑和已审计语义冻结，防止后续验证阶段为通过验证而削弱安全定义。

### 2.3 程序验证阶段

- **按需语义扩展**：若程序使用未支持 API，则用同一语义生成管道补充语义；已有语义保持冻结。
- **翻译**：翻译智能体将程序转为 Dafny，并附加所需安全规范；批评智能体检查翻译忠实性。形式化保证针对经过验证的 Dafny 实现及其编译输出，而非直接针对原始源码。
- **证明规划与修复**：
  - 规划智能体生成多个候选证明策略和轻量注解草图，先用验证器探测，再并行探索。
  - 每个计划初始化独立的注解-修复过程：先添加证明注解且不改变可执行行为；必要时允许代码修复。
  - 批评智能体审查注解忠实性、稳定性和修复的功能保留性。
  - 允许添加辅助引理，但不能修改冻结语义。
  - 确定性检查拒绝证明绕过构造，如 `assume`、公理或禁用验证。
  - 环境假设通过运行时 `expect` 检查暴露。

- **编译回源语言**：使用 Dafny 内建编译器将验证后的 Dafny 编译为目标语言；系统通过确定性符号映射将领域 API 符号替换为真实源语言 API。
- **战术学习**：验证后提取可复用证明策略，包括不变式模式和求解器稳定技巧，形成战术库供后续任务复用。

## 6. 论文的主要结论与发现

- **统一框架可行**：同一套程序级验证流程在 CUDA、终端、机器人三个执行模型差异很大的领域中，均可产生 Dafny 验证通过的输出，验证成功率为 220/220（100%）。
- **独立安全检查结果**：
  - CUDA 100/100、机器人 20/20 通过独立安全检查。
  - 终端只有 82/100 通过，18 个失败集中在特权访问和并发相关 CWE，说明自动形式化语义未完全覆盖安全相关行为。
- **功能保留结果**：
  - CUDA 100/100、终端 100/100 通过 held-out 功能测试，说明在这些领域可以在不牺牲被测试功能的情况下附加形式化安全保证。

- **核心洞察**：验证器健全性本身不够，实际保证强度取决于底层语义的覆盖和保真度。终端失败源于语义覆盖不足；机器人失败源于语义过粗或过强，导致功能空泛但形式安全的修复。
- **成本结论**：每个样本平均 36–68 分钟、8.6–10.2 美元，适合安全关键或高后果代码生成，不适合常规快速原型开发。

## 7. 优点

- **可复用的领域语义**：将 API 和安全需求形式化一次并冻结，后续任务无需人工逐程序证明，降低了形式化验证的门槛。
- **验证与执行分离**：通过 Dafny 中间表示，同一框架可适配完全不同的目标语言和执行模型。
- **多智能体分工明确**：语义生成、翻译、证明规划、修复、批评和战术学习解耦，便于错误定位和扩展。
- **防止“证伪”机制**：冻结语义、确定性拒绝 `assume`/公理等证明绕过构造、环境假设暴露为运行时 `expect` 检查，有助于保证证明并非空洞。
- **独立评估设计**：使用 Compute Sanitizer、SecCodePLT 安全测试、MuJoCo 碰撞/越界指标等外部 oracle，以及独立的 held-out 功能测试，能够揭示语义覆盖不足和空泛修复两类问题。
- **成本透明**：提供了时间、token 和美元开销，有助于判断实际适用性。
