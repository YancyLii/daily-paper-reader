## 摘要
LLM 智能体会执行真实操作，包括运行代码、修改文件、调用服务与委托任务，这些操作由上下文来源驱动：用户请求、工具结果、文档、shell 输出、Skill 与 MCP 指令、记忆。与传统系统中能力预先定义不同，智能体所需的最小权限能力是动态的，取决于其任务意图：它想做什么以及如何做。这带来了安全（security）与安全性（safety）挑战：所有输入都进入一个共享的规划通道并具有同等影响力，可能因对抗性注入或意外的范围扩大而被利用，然而用户的明确请求与文档中提取的文本具有不同的信任级别，不应共享选择目标或扩大访问权限的权威。现有防御机制约束操作与信息流；我们研究任务范围限定、多来源的权限组合。我们认为，智能体的能力应限定在当前任务意图范围内，而非沙箱或会话生命周期内，并且没有任何单一上下文来源能够定义完整的能力。IntentCap 从四个这样的来源组合能力：用户意图、工作流指令、工具模式与运行时环境，并具备字段级所有权与单调收窄。每个来源贡献特定字段，任何来源都不能填充另一个来源的字段，且租约只会收窄用户已授权的权限，绝不会扩大权限。IntentCap 使用 LLM 从这些来源生成短期租约，在任何副作用提交之前由确定性检查器验证，并通过工具级与操作系统级的信息流策略强制执行。评估表明，IntentCap 能在不拒绝良性操作的情况下阻断所测试的违规行为，每个来源边界都是独立必要的，且检查器能够跨工具、执行、放置和委托边界进行泛化。

## Abstract
LLM agents take real actions, including executing code, modifying files, calling services, and delegating tasks, driven by context sources: user requests, tool results, documents, shell outputs, Skill and MCP instructions, memory. Unlike traditional systems, where capability is predefined, the least-privilege capability an agent needs is dynamic, depending on its task intent: what it wants to do and how. This creates a security and safety challenge: all inputs enter one shared planning channel with equal influence, by adversarial injection or accidental scope widening, yet a user's explicit request and a document's extracted text carry different trust and should not share authority to choose a destination or widen access. Existing defenses constrain operations and information flow; we study task-scoped, multi-source authority composition.   We argue that agent capabilities should be scoped to the current task intent, not a sandbox or session lifetime, and that no single context source defines a complete capability. IntentCap composes capabilities from four such sources: user intent, workflow instructions, tool schemas, and runtime environment, with field-level ownership and monotonic narrowing. Each source contributes specific fields, none can fill another's, and the lease only narrows the user's authorized authority, never widens it. IntentCap uses an LLM to generate short-lived leases from these sources, validated by a deterministic checker before any side effect commits and enforced by tool- and OS-level information flow policies. Evaluation shows IntentCap blocks tested violations without rejecting benign actions, each source boundary is independently necessary, and the checker generalizes across tool, execution, placement, and delegation boundaries.

## 2. 论文提出的方法论

- **核心思想**：IntentCap 在运行时从四个上下文来源组合能力，并实现字段级所有权（field-level ownership）与单调收窄（monotonic narrowing）。
- **四个上下文来源及其贡献字段**：
  - **用户意图**：目标、选定对象、授权目标、审批范围；
  - **工作流指令**（系统策略、Skill 流程、手册）：程序性范围；
  - **工具模式**（MCP 定义、注册表、命令描述）：可调用接口和凭证范围；
  - **运行时环境**（工具结果、文件状态、脚本输出）：观测到的值。
- **字段级所有权规则**：每个决策字段只能由一个来源拥有，例如工具模式不能授权目标、运行时环境不能提供程序性权限、Skill 不能扩大审批范围。
- **能力租约（capability lease）**：绑定字段贡献到具体操作、对象、参数、预算、过期时间、委托深度；租约只能收窄用户授权，不能扩大；一次性使用后过期。
- **系统架构与 TCB（可信计算基）**：
  - 不可信部分：LLM 规划器和编译器（可被任意操纵，只提出候选租约，不决策）；
  - 可信部分（TCB）：意图签发器（intent issuer）、来源标记器（source labeler）、确定性检查器（deterministic checker）、执行层（挂钩、MCP 网关、OS 执行器）。
  - 来源标记器按位置分类输入：用户消息=用户意图；工具响应=运行时环境；Skill/MCP 元数据在加载时标记；来源模糊的输入保守地拒绝授权字段。
- **检查器接口**：`check_and_consume(e, lease, proofs, σ) → allow(σ') | deny`，所有副作用提交前必须调用；委托进一步衰减（子任务只能获得比父任务更窄的能力）。
- **执行层**：工具级边界适配器拦截 MCP 调用并验证参数字段来源；OS 级将接受的租约编译为 ActPlane 文件、执行、网络策略，通过 eBPF 强制执行。
- **算法流程概述**：来源标记 → 意图签发器提取用户最大权限 → 不可信编译器生成候选租约 → 确定性检查器验证字段来源与单调收窄 → 通过后执行副作用并记录审计。

## 6. 主要结论与发现

- IntentCap 在测试事件上实现 **0 个不安全接受**，且不拒绝良性动作（覆盖所有 3,813 个良性参考动作，通过 2,554/2,556 适用检查）。
- **四源划分是安全要求而非命名选择**：折叠为单一来源导致 94% 误接受；成对折叠分别产生 50%、43%、43% 的误接受。
- 仅用策略 DSL 检查谓词无字段所有权的方案在 7 个多步工作流上全部误接受；独立守卫拆分状态 5/7 失败。
- `check_and_consume` API 可泛化到五个执行点，38 项检查中 0 个不安全执行/放置、0 个检查器/监控不一致。
- 租约作为可审计权威对象：24 个手工标注租约全部匹配预期范围；所有非 IntentCap 基线在至少部分策略条目上过度授权。

## 7. 优点

- **安全模型清晰**：字段级所有权和单调收窄原则简洁且针对性强，抓住了多源上下文权限组合的核心问题。
- **TCB 最小化**：LLM 保持不可信，仅提出候选；确定性检查器做最终决策，降低模型操纵风险。
- **来源标记与审计**：按位置和进程来源标记，提供可追溯的审计链。
- **多层次执行**：工具级拦截与 OS 级策略（ActPlane/eBPF）结合，覆盖不同边界。
- **实验覆盖较广**：使用多个真实攻击数据集，验证从工具调用到委托、执行、放置等多类边界。
