## 摘要
反编译从编译后的机器代码中恢复高级源代码，并作为漏洞检测和恶意软件分析等安全任务的基础。传统的反编译器（如 Ghidra 和 Hex-Rays）将无法解析的内容暴露为可见占位符，并且经常生成无法编译或执行的伪代码；基于 LLM 的反编译器生成干净、地道的 C 代码，现在几乎完全根据可重编译性和可重执行性来评判：输出是否能够构建并通过其自带的输入/输出测试。我们表明这些指标可能会奖励错误的路径：一个函数可能重编译并通过所有自带的测试，但在其他合法输入上产生分歧，并且已披露的漏洞可能会从重编译的代码中消失，而没有可见的崩溃痕迹。现有测试套件均未捕获这两种失败。为了解决这一差距，我们提出了 Decompile-Diverge，一种不依赖固定或手工测试的行为比较预言机：对于每个函数，它合成一个驱动程序，从参考实现中增长模糊测试语料库，并在相同输入上重新运行反编译代码，以检测函数行为的变化。在已建立的 LLM 反编译语料库上，针对八个系统九种配置，通过所有自带测试的候选代码在我们的输入语料库上仍然与原始代码存在分歧：总体为 4.9%，单个系统高达 13%。在 300 个真实的 GitHub 库函数和 287 个基于 CVE 的函数上，可重编译性和行为一致性可能分离：最强的精化 LLM 将 Ghidra 的构建率从 75% 提高到 90%，而其匹配率从 74% 下降到 62%；在已披露的漏洞上，多达十分之一的输出表现出崩溃缺失。源代码级分析将这种分歧追溯到引入的字段、类型、被调用者和守卫，它们取代了传统工具留下的可见未知项。

## Abstract
Decompilation recovers high-level source from compiled machine code and serves as a foundation for security tasks such as vulnerability detection and malware analysis. Traditional decompilers like Ghidra and Hex-Rays expose whatever they cannot resolve as visible placeholders and often emit pseudocode that will not compile or execute; LLM-based decompilers produce clean, idiomatic C and are now judged almost entirely by recompilability and re-executability: whether the output builds and passes its shipped input/output tests. We show that these metrics can reward the wrong path: a function may recompile and pass every shipped test yet diverge on other legitimate inputs, and a disclosed vulnerability may disappear from the recompiled code with no visible trace of the crash. Neither failure is caught by existing suites.   To address this gap, we propose Decompile-Diverge, a behavioral comparison oracle not relying on fixed or hand-crafted tests: for each function it synthesizes a driver, grows a fuzzing corpus from the reference, and reruns the decompiled code on the same inputs to detect changes in the function's behavior. Across eight systems in nine configurations on established LLM decompilation corpora, candidates that pass every shipped test still diverge from the original on our input corpus: 4.9% overall, and as many as 13% for a single system. On 300 real GitHub library functions and 287 CVE-grounded functions, recompilability and behavioral agreement can come apart: the strongest refinement LLM lifts Ghidra's build rate from 75% to 90%, while its Matched rate falls from 74% to 62%; on disclosed vulnerabilities, up to one tenth exhibit Crash Absence in its output. Source-level analysis traces this divergence to introduced fields, types, callees, and guards that replace the visible unknowns traditional tools leave behind.

## 1. 论文的核心问题与整体含义

- **研究背景**：反编译是漏洞检测、恶意软件分析等安全任务的基础。传统反编译器（如 Ghidra、Hex-Rays）会暴露无法解析的占位符（如 `undefined4`、`DAT_*`），输出的伪代码常不可编译；而基于 LLM 的反编译器能生成干净、地道的 C 代码。
- **核心问题**：当前 LLM 反编译器几乎完全以“可重编译性”和“可重执行性”（即能否构建并通过自带输入/输出测试）作为评测指标，但这些指标可能奖励错误行为。
- **具体表现**：
  - 一个函数可能重编译并通过所有自带测试，但在其他合法输入上行为分歧（Divergence）。
  - 已披露的漏洞可能在重编译代码中消失，且无可见崩溃痕迹（Crash Absence）。
  - 现有测试套件无法捕获这两种失败。
- **整体含义**：需要更可靠的行为级评测方法，以暴露 LLM 反编译器在“代码更干净、可编译”表象下的行为保真度损失。

## 2. 论文提出的方法论

- **核心思想**：提出 **Decompile-Diverge**，一种不依赖固定或手工测试的行为比较预言机（behavioral comparison oracle）。
- **关键流程**：
  1. **驱动合成**：为每个目标函数自动合成驱动程序。
  2. **语料生成**：使用 AFL++ 对参考实现（原始 C 函数）进行模糊测试，动态增长输入语料库。
  3. **行为比较**：将反编译得到的候选代码原样拼接到驱动中，在完全相同的输入上执行。
  4. **状态比较**：比较参考实现与候选代码的“有界可观察后状态”（bounded observable post-state），包括返回值、写入的字节、可写全局变量、`.data` 和 `.bss` 区间（以链接器符号为界）。
- **关键技术细节**：
  - 使用 AddressSanitizer 构建以检测崩溃和挂起；使用未插桩的 `-O0` 构建比较后状态。
  - 指针值在摘要中被重定位掩码，以排除内存布局变化的影响。
  - 在 GitHub 和 CVE 轨道上，分歧只有在参考与候选各四次重跑中均复现时才计数，以排除地址空间布局或未初始化内存造成的抖动。
- **判定标签**（仅对成功构建的候选）：
  - `Matched`：在所有输入上与参考一致。
  - `Divergence`：在至少一个输入上行为改变（包括输出变化、崩溃、挂起等）。
  - `Crash Absence`：仅在 CVE 轨道报告，指参考实现预期崩溃但候选代码不再崩溃；该标签优先于 `Divergence`，保证标签互斥。
- **重要性质**：由于比较受限于生成的语料和有界可观察后状态，`Matched` 率是行为一致性的上界，而 `Divergence` 和 `Crash Absence` 率是下界。

## 6. 论文的主要结论与发现

- **通过自带测试仍存在显著分歧**：在四个已建立语料库上，通过所有自带测试的候选中，仍有 **4.9%** 在生成的语料上分歧，单个系统最高达 **13%**（Nova 在 HumanEval 上）。
- **构建率与行为一致性分离**：
  - 在 GitHub 真实代码上，LLM4Decompile 将 Ghidra 的构建率从 **75% 提升到 90%**，但匹配率从 **74% 下降到 62%**。
  - 精化系统普遍以行为一致性为代价换取构建率提升。
- **漏洞代码出现崩溃缺失**：
  - 在 CVE 轨道上，LLM4Decompile 将 Ghidra 的构建率从 30% 提升到 64%，但在 183 个构建中，有 25 个丢失了参考崩溃，即 **Crash Absence 率为 8.7%**（95% CI [6.0%, 12.5%]）。
  - 原始 Ghidra 没有 Crash Absence 案例；GLM-5.2-E2E 在 66 个构建中有 11 个丢失崩溃。
- **源码级归因**：
  - 分歧主要源于引入的字段、类型、被调用者和常量守卫，而非继承自传统前端的错误。
  - LLM 系统倾向于“自信地发明”替代传统工具留下的可见未知项；引入符号的候选分歧率显著更高（GitHub 上 53% vs 20%，优势比 4.6）。
  - 精化系统移除前端词汇比例高（40–98%），而 DeGPT-Qwen 编辑保守，行为最接近前端。
- **失败模式迁移**：从传统反编译器的“可见未知项”转变为 LLM 的“自信发明”，这些发明可能通过编译但在运行时改变行为或消除崩溃。

## 7. 优点

- **方法创新**：提出 Decompile-Diverge，不依赖固定测试，利用模糊测试动态生成语料，能够发现自带测试未覆盖的行为分歧。
- **行为级评测**：比较有界可观察后状态，独立于内存布局，减小了环境噪声影响。
- **覆盖面广**：

- **未覆盖所有现有系统**：部分近期工作（如 DecLLM、SALT4Decompile、D-LiFT 等）因公开工件不足而未纳入对比。
- **外部有效性**：结论主要基于 C 语言反编译场景，对其他语言或更复杂二进制类型的适用性尚待验证。
